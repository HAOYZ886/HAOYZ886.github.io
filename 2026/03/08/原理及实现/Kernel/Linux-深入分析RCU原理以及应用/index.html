RCU的基本概念

RCU 的英文全称是 Read-Copy Update ，它是用在读多写少的场景下的无锁机制。它支持读和写并行操作，但是不允许多个写操作同时对同一个资源进行操作，需要额外的同步机制，比如自旋锁。它与读写锁相比，最主要的区别就是读操作并不需要与写操作同步，这样就能大大提升了并发并行的性能，同时临界区的扩展性增强，而且无死锁风险。
那么 RCU 的读写操作并行是如何保证的？从 RCU 英文全称去解析，Reader 读取共享资源，Updater 获取一个新的内存空间，把该共享资源的数据复制到新的内存空间，并进行进一步的写操作，再作为该共享资源的新版本（Update）。一般来说，RCU 仅允许有多个 Readers 和一个 Updater 同时去操作同一个共享资源。当有一到多个 Readers 正在进行读操作时，Updater 正在更新共享资源，当 Updater 更新完成后，这批 Readers 还在进行读操作，这时 Updater 是不能对该旧版资源回收，而是等待它们读操作完成才能回收。而新来的 Reader 则是可以直接读新版本的共享资源即可。总得来说，Updater 更新完成新版本的共享资源后，还要对上一个版本的共享资源回收。

根据以上的概念，这里引出了一个问题，Updater 是怎么知道没有任何 Readers 访问旧版本资源？

先回顾线程的原理（不管线程还是进程，都是调度对象，这里统称用线程来表示），线程运行的环境分为内核层和用户空间。而处于用户空间的线程是：

  • 可以通过系统调用主动进入内核层，但仍处于进程上下文；
  • 也可以被中断/异常被动进入内核层，但属于中断上下文。

另外，已知 Linux 内核被分为可抢占内核和不可抢占内核。可抢占内核的原理是：当在内核层的线程被动进入中断，且准备从中断返回前，判断能否被抢占。满足可被抢占需要两个条件：

  1. preempt_count 等于 0 ；
  2. 当前线程被标记为 NEED_RESCHED 。

这更对 synchronize_rcu() 的实现感到好奇了，这究竟是怎么让 Updater 知道 Reader 已经完成读操作？
这里我们需要回顾一下锁的机制，来推理 RCU 的实现机制。首先，无论是什么锁，都需要一个空间来记录锁的状态，比如“已被持有”或“未被持有”。那 RCU 呢？回看以上例子，RCU 的 API ，尤其是生成读临界区的 API ，没有发现显式的内存空间，来记录这个线程或执行该线程的 CPU 的 RCU 状态。那就只有当 CPU 不执行该执行流，才能表示当前读操作的结束，这就是从空间换取为时间。对于非可抢占内核，不管是内核线程，还是通过系统调用进入内核层的应用进程，在内核层都不会被动调度，只有主动调度；对于可抢占内核，在内核层，只要被标记为 NEED_RESCHED ，且抢占计数为 0 ，则从中断上下文返回前被调度。所以也从中发现 rcu_read_lock() 和 rcu_read_unlock() 在不同内核的实现差异。在可抢占内核，在 RCU 读临界区必须要把抢占关闭，不然提前被调度，会被系统误以为读操作已完成，把旧资源清除，从而出现野指针，后果不堪设想。
在新版本的资源的发布之后，在旧资源回收之前的时期被称之为“宽限期”（Grace Period）。宽限期的结束依赖 Reader 对旧资源的读临界区释放，每当一个 Reader 读操作完成，就表示进入“静默状态”（Quiescent State）。通过以上 rcu_read_lock() 和 rcu_read_unlock() 的实现可知，这里没有明显的表示“静默状态”。但是可以使用“当前线程被调度”作为一个明显的信号来表示，事情是否简单了起来？
另外，对于那些执行用户进程的 CPU 和处于 IDLE 状态的 CPU ，它们很明显没有进入 RCU 的读临界区，所以应当把它们默认标记为静默状态。
通过以上讲述得知，RCU 是非常注重时间的，在资源回收上，仅关注运行时的执行流，而 CPU 是执行执行流的对象，所以用 Pre-CPU 变量和位图（一个 CPU 对应一个 Bit ）来隐式表示即时执行流的“静默状态”，这是经典 RCU 的主要实现。所以，当所有的 CPU 都进入“静默状态”后，说明已经没有任何 Reader 对该旧资源访问，表示宽限期已经结束，可以清除并释放该资源。

这里产生一个疑问，上述的理论是围绕着整个系统仅有一个 RCU 的资源回收来简述，如果有多个资源需要回收呢？一个 CPU 有多个不同的资源需要回收呢？多个 CPU 各自有一个资源需要回收呢？

我们先基于以上理论来思考 RCU 的实现，假设一个系统有 4 个 CPU ，现在的 RCU 实现要求很简单：每次仅有一个旧资源回收，且回收完成前不会再接收旧资源回收请求。则仅有一个 CPU 在进行更新和旧资源回收操作，当当前宽限期结束后，才能有下一个旧资源回收请求。
先思考一下，需要一个全局变量 GP 来记录当前系统是否存在宽限期，这里简单一点，数据类型为 Bool 即可，为 True 时，表示存在宽限期。那么当一个 CPU 发出宽限期后（GP=True），其它 CPU 是如何知道宽限期已经出现？
目前的做法是用“主动轮询”机制。使用调度定时器（假设触发频率为：100Hz），让每个 CPU 在它的中断上下文期间，主动查询全局变量 GP 是否有宽限期了。另外还需要一个全局的位图，名为 qs_cpu_bitmap ，用于记录各个 CPU 的静默状态。生成新的宽限期时，该位图的 Bit 都被置位；当位图的 Bit 都被清除时，就表示所有 CPU 都进入静默状态，当前系统的宽限期已结束，可以回收资源。
那么 CPU 又是该如何上报它当前已经是静默状态？经过以上讲述得知，可以把“当前线程被调度”信号作为一个数据类型为 Bool 的 Pre-CPU 变量，名为 passed_quiesc 。当信号触发后，该变量为 True ，当出现新宽限期时，在此之前该变量必须被设为 False 。当处于调度定时器的中断上下文的 CPU 发现它自己的 passed_quiesc 为 True 后，即可把位图 qs_cpu_bitmap 对应的 Bit 清除即可。

问题 1 ，在具体实现中，宽限期是在调用 call_rcu() 后开始？还是在调用 call_rcu() 后的执行第一个调度定时器的中断处理程序开始？
问题 2 ，因为回调函数 ->rec_cb() 在中断上下文处理，不管是硬中断还是软中断，如果旧资源回收请求越来越多，从而直接导致中断上下文过长，线程得不到执行权，这时该怎么办？

带着以上问题，再进行一次需求升级，要求在同一个 CPU ，可随时发出旧资源回收的请求，如果系统已经存在宽限期，也能正常发送该请求，这又该如何实现？
从理论上讲，每一个旧资源回收请求都它自己的一个宽限期。但根据以上讲解可知，这是实现是很复杂的。我们应先遵循“先能用再到好用”原则，从简设计，把多个宽限期合并为一个时间跨度较大的宽限期。因为这里有一个不可避免的情况，CPU 正在执行的线程，它可以不仅作为共享资源 A 的读者，它也可以作为共享资源 B/C/D 等等的读者。
所以目前简单的做法是当已存在一个宽限期时，又来了一到多个旧资源回收请求，则把 qs_cpu_bitmap 的 Bit 重新置位，重新开始。见以下流程图：

问题 3 ，如果宽限期已存在的情况下，总是有源源不断的旧资源回收请求，导致 qs_cpu_bitmap 频繁被重新置位，导致宽限期迟迟无法结束，再导致先前的旧资源迟迟得不到回收，出现 OOM ，该怎么办？

在这里有必要回答问题 1 ，其实两种都可以，在这任意两种中选一个去实现宽限期的起始阶段。它们的实现方法是一致的（又或者说这样区分是没有必要的）：

  1. 把变量 gp 的数据类型从 bool 改为 int ，记录是哪个 CPU 发出的。还需要数据类型为 int 的变量 done ，也是记录 CPU ，来记录宽限期的完成。
  2. 把链表 rcu_head 分为三部分：next_list、cur_list 和 done_list 。它们的作用分别是：
    • next_list：记录准备开始宽限期的旧资源回收请求
    • cur_list：记录正在进行宽限期的旧资源回收请求
    • done_list：记录宽限期已完成的旧资源回收请求
    • 结合流程：当调用 call_rcu() 时，把请求放到链表 next_list ；在执行调度定时器的中断处理程序时，发现链表 next_list 不为空，则把它的成员移动到 cur_list ，进行新的宽限期；当所有 CPU 都进入静默状态，表示宽限期结束，则把所有链表 cur_list 的成员移动到 done_list 。
  3. 强制要求哪个 CPU 发出的请求，哪个 CPU 来处理（包括回收链表的管理）。假设 CPU0 发送请求，如果 CPU1 是最后一个进入静默状态，且由它执行相关回调操作，而 CPU0 在进入调度定时器中断前发送一个新的请求，则 CPU1 极大概率会提前执行 CPU0 刚刚发出的请求所对应的回调函数。
