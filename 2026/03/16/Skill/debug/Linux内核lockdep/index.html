Linux - Lockdep调试

Posted on 2026-03-16 Edited on 2026-03-17 In Skill Word count in article: 4.1k Reading time ≈ 15 mins.

前言

死锁检测 Lockdep 是 Linux 的 DEBUG 功能之一。死锁一般分为 ABBA 死锁和递归死锁。

开启死锁检测后，当出现或疑似出现死锁时，会发出对应的 DEBUG 信息，开发者可以以此信息分析并找到造成死锁的代码。

内核配置

内核需要开启以下配置：

  • CONFIG_PROVE_LOCKING：运行时进行锁验证，检查锁的正确使用情况，以防止潜在的死锁和竞争条件。
  • CONFIG_DEBUG_LOCKDEP：运行时进行锁验证，且具备更细致的自检机制。
  • CONFIG_LOCK_STAT：收集有关锁的统计信息，包括锁的使用次数、等待次数等。这些统计信息对于锁的性能分析非常有用。

配置完成后需要重新编译内核，而且内核镜像会增加几 MB ，需要额外注意存储镜像的分区是否足够容纳，以及内核在内存分布（是否会影响预留内存等）。而且内核的执行效率也会有影响，不太适合在生产阶段使用。

这段信息报告：在函数 hack_spin_again() 在获取锁 hack_spinlock 时疑似出现递归死锁，还指明了该锁已在函数 hack_spin() 获取。但这段信息并没有说明是在同一个 CPU 出现的，需要看下一段信息才能知晓。

信息“{+.+.}”代表了锁hack_spinlock经历过的，或正在经历的状态。先看状态的类型：

类型 描述 安全性
‘.’ 在中断关闭，在非中断上下文获取锁 安全性最高，没有中断打扰
‘-‘ 在中断关闭，在中断上下文获取锁 安全性欠佳，要确认非中断上下文获取锁前是否已关闭中断
‘+’ 在中断开启，在非中断上下文获取锁 安全性欠佳，要确认中断上下文是否需要获取该锁
‘?’ 在中断开启，在中断上下文获取锁 安全性最差，当出现中断嵌套时出现死锁的概率最大

知晓状态类型后，信息“{+.+.}”中有四个状态，这又是怎么回事？以下截自 Documentation/locking/lockdep-design.rst 的原话：

When locking rules are violated, these usage bits are presented in the locking error messages, inside curlies, with a total of 2 * n STATEs bits.

其中 n 一般为 2 ，即 hardirq 和 softirq 。即信息“{+.+.}”的前 2 个状态是代表 hardirq ，后 2 个状态是代表 softirq 。

那为什么一个 irq 需要两个状态位？这是因为还考虑到了读写锁，第一个和第三个状态位代表写锁，第二个和第四个状态位代表读锁。而对于自旋锁和互斥锁，则只关心第一个和第三个状态位即可，分别对应 hardirq 和 softirq ：

锁的使用状态查询

使用以下命令查看状态：

以下是一个输出片段：

  • 0000000027522a39：是锁devpts_mutex的唯一标识符。
  • OPS：表示锁devpts_mutex已被获取的次数
  • FD：指的是该锁的依赖深度（Forward Dependency），即在这个锁之后被获取的锁的数量。FD=30 表示在内核运行过程中，曾经有代码路径在持有devpts_mutex后，还额外获取另外30个锁。
  • BD：指的是该锁的回溯深度（Backward Dependency），即在获取这个锁之前，已经有多少个锁被持有。BD=3 表示在内核运行过程中，曾经有代码路径在持有另外3个锁的情况下，尝试获取 devpts_mutex

箭头 -> 开头的每一行，都代表了内核代码中实际发生过的、且被 lockdep 记录下来的锁获取顺序 。这形成了一个链：当持有 devpts_mutex 时，代码又依次（或在其他代码路径中）获取了下面这些锁。
