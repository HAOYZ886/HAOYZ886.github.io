Linux - 使用“GPIO+示波器”的方式观测实时抖动

Posted on 2026-04-15 Edited on 2026-04-16 In 原理及实现 Word count in article: 3.1k Reading time ≈ 11 mins.

前言

现在在想，能否用 GPIO+示波器 的方式去测试实时抖动？通过之前的文档可知，实时操作系统的核心在于确定性，所以我们首要关心的是，在进行长时间的持续测试中，延迟抖动的最大值是多少，以此确定 RTOS 的确定性；其次是平均值是多少，以此确定 RTOS 的性能。
见以下例图，使用 cyclictest 能测试出“中断发出->中断响应->任务唤醒->任务调度->返回到用户空间”的总体耗时。

如果通过 GPIO+示波器 的方式去观测，目前我能想到的，就是写一个内核模块以及一个用户空间测试程序。用户进程通过系统调用陷入内核层，并计时睡眠。当定时器触发并唤醒该进程，唤醒前把 GPIO 拉高。用户进程被调度执行，并返回到用户空间后，再到把该 GPIO 拉低。这个区间作为一个“任务唤醒->任务调度->返回到用户空间”的耗时，并显示到示波器上。
为什么无法在示波器上“中断发出->中断响应”的延迟？从实现难度上讲，就需要在中断发出时立即把 GPIO 拉高，但是中断从发出到 CPU 响应，这也需要时间，这是无法实现的。
那能否再用一个 GPIO ，记录用户进程进入内核层，到发出 hrtimer 定时的执行时间？这是可以的，但仅能估算出中断延迟的平均时间，无法计算出中断延迟的最大时间（详情见以下实践部分）。

另外，还需要额外注意的，就是通过 MMIO 访问 GPIO 的寄存器并置位，再到 GPIO 的电平拉高/拉低指定电压（上升沿/下降沿的抖动），这也是延迟，属于硬件延迟，这个根据 SoC 而定。

所以，总得来说，GPIO+示波器 的方式去观测实时抖动，只能用作于展示，个人认为这还是一个玩具，但借此去再次深入理解 RTOS 的实时抖动还是挺有意思的。

系统架构概述

源码下载地址：

该测试套件包含一个内核驱动模块和一个用户空间测试程序，通过 GPIO 的电平变化来可视化系统的实时抖动。
该套件由两部分组成，协同工作以测量从“进程唤醒”到“用户进程实际执行”的时间差：

  • 内核模块 (gpio_jitter.c)：负责产生定时中断、在中断上下文中标记时间（拉高GPIO），并唤醒用户进程。
  • 用户程序 (app_jitter.c)：负责在被唤醒后第一时间执行动作（拉低GPIO），并直接操作硬件寄存器以减少软件开销。

核心工作流程与原理

整个测试过程模拟了一个实时事件的处理链，其核心时序原理如下：

  • 阶段一：初始化与配置

    • 用户程序通过 ioctl 将GPIO的物理地址、引脚号、定时器间隔等配置传递给内核模块。
    • 内核模块使用 ioremap 将物理地址映射为内核虚拟地址，并初始化高精度定时器 (hrtimer) 和同步机制（等待队列或完成量）。

  • 阶段二：触发测试，用户程序调用 read 函数进入阻塞状态（模拟等待事件）。

    • 可选，用户程序调用 read 前，把 GPIO1 拉高，记录睡眠前执行耗时的起点。
    • 内核模块的 rt_jitter_read 函数被调用，它执行 test_cb 回调。
    • 回调函数启动 hrtimer，把 GPIO1 拉低，记录睡眠前执行耗时的结束（可选）。
    • 当前进程进入睡眠等待状态（通过 wait_event 或 wait_for_completion）。

  • 阶段三：中断响应（时间点 T1）

    • 当定时器到期，内核产生硬件中断。
    • 在中断上下文（高精度定时器）中，回调函数 timer_callback 被执行。
    • 关键动作：立即执行 pin0_set() 拉高 GPIO0。这是时间点 T1，代表“硬件中断触发的时刻”。

  • 阶段四：进程唤醒与执行（时间点 T2）

    • 紧接着，内核调用 wake_up_interruptible 或 complete 唤醒正在睡眠的用户进程。
    • 调度器介入，将用户进程调度到CPU上运行。
    • 用户进程从 read 调用返回，立即拉低 GPIO0。这是时间点 T2，代表“用户进程实际处理事件的时刻”。

测量结果

通过示波器观察 GPIO0 的电平：

  • 高电平波形宽度 = T2 - T1
  • 这个时间差即为任务唤醒+调度的实时响应延迟，包含了中断处理延迟（部分）和进程调度延迟（主要）。

计算中断延迟

现在来尝试通过两个 GPIO 的波形，来计算中断延迟。

其中黄色正波形是“任务唤醒->任务调度->返回到用户空间”的延迟，黄色负波形是“进入内核层->本身hrtimer函数的执行时间->32us定时->中断响应->部分hrtimer的执行执行时间（执行唤醒函数前）”的延迟。
而绿色正波形是““进入内核层->本身hrtimer函数的执行时间”，绿色负波形是“32us定时->中断响应->部分hrtimer的执行执行时间（执行唤醒函数前）->任务唤醒->任务调度->返回到用户空间”的延迟。
我想借此计算出中断延迟，先根据各波形的最小值来计算中断延迟的最小值，比如黄色正波形为5.02us，负波形为34.65us；绿色正波形为1.195us，负波形为38.264us，已知定时为32us，则中断延迟大约为：34.65-(1.195+32)=1.455us 。其实这种方法也能用于计算中断延迟的平均值。

但这种方法计算不了中断延迟的最大值。
期间我试过用绿正波形的最大值和最小值，分别计算中断延迟的最小值和最大值。但是，我忽略了跨周期的极值混搭会导致计算结果失去真实对应关系，就比如：
黄色负波形的最大值 来自某个周期（记为周期A）：

  • 黄负_max = 32us + 中断延迟_A + 绿色正_A
    绿色正波形的最大值 来自另一个周期（记为周期B）：
  • 绿正_max = 内核+hrtimer执行时间_B
    绿色正波形的最小值 来自又一个周期（记为周期C）：
  • 绿正_min = 内核+hrtimer执行时间_C

假设周期 A 中，黄色负波形很大是因为 “中断延迟很大 + 内核/hrtimer执行时间也很大（比如绿正=3us）”。
而周期 C 中，绿色正波形很小（比如绿正=1us），是因为内核/hrtimer执行时间很短，但那个周期里的黄色负波形可能很小（比如实际中断延迟只有0.5us）。
用 黄负_max（来自周期A，含3us绿正） - 32us - 绿正_min（来自周期C，1us），得到的结果是：

  • (32+中断延迟_A+3) - 32 - 1 = 中断延迟_A + 2us。

这个 2us 完全是因为混用了不同周期的绿正值而产生的虚假增量，真实的中断延迟_A可能只有1us。
最终得到的“中断延迟最大值”可能比真实最大值大很多，甚至出现不合理的大值；而“中断延迟最小值”也可能比真实最小值小很多。这两个极值从来没有在一个真实的物理周期中同时出现过。
