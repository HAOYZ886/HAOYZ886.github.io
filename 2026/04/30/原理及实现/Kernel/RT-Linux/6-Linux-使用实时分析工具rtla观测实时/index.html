Linux - 使用实时分析工具rtla观测实时

Posted on 2026-04-30 Edited on 2026-05-15 In 原理及实现 Word count in article: 9k Reading time ≈ 33 mins.

什么是rtla

rtla 的全称为 Real-Time Linux Analysis ，它是一个基于 FTrace 的实时分析工具集，已在 Linux 5.17 集成。它与 cyclictest 类似，但不同的是，它能监测出中断响应，以及任务唤醒到任务执行之间的抖动延迟；还能监测系统噪音检验任务的可观测性。

系统噪音：指的是一个任务在可运行期间被强行打断，如被高优先级的线程抢占、IRQ、SoftIRQ、NMI 和 SMI 等。

rtla 背靠 FTrace 的 osnoise 和 timerlat 机制，不仅能量化系统的调度延迟与抖动，更能自动定位产生高延迟的根本原因（如中断屏蔽、长临界区或硬件干扰）。也由此可知，它解决了 cyclictest 只能测“延迟有多大”却无法回答“延迟从哪来”的痛点。

定义与核心特性

rtla 是一个前端工具，它的后端是 FTrace 的 osnoise 和 timerlat ，所以它属于白盒测量。而传统的延迟测试工具（如 cyclictest），则是采用黑盒测量。
cyclictest 的基本实现是：为每个 CPU 新建一个高实时优先级的应用线程，主动调用 nanosleep() 休眠并等待唤醒，通过计算预期唤醒时间与实际唤醒时间的差值，以此得到一个延迟样本。
cyclictest 无法与内核直接建立“联系” ，它仅能计算整体的延迟，见以下例图：

整体的延迟包含：

  • Timer 的“硬件中断触发->内核响应中断”的延迟；
  • Timer IRQ 的执行耗时（包含唤醒）；
  • 调度以及任务切换的耗时；
  • 从内核层返回到用户空间的耗时；
  • 还有可能隐含的硬件延迟。

类似的，rtla 也为每个 CPU 新建一个高实时优先级的内核线程，除了捕获整体延迟外，还能捕获中断响应的延迟，而整体延迟被命名为线程响应延迟。而且当检测到延迟超过阈值时，它会自动触发内核追踪，抓取当时的调用栈、中断状态和调度信息，将延迟拆解为可理解的组成部分，实现从“盲目调优”到“精准定位”的转变。

测量目标：延迟与噪声

rtla 的核心目标是量化与分析影响实时性的两大阻碍：调度延迟与系统抖动/噪声。它通过两个核心子命令 timerlat 和 osnoise 覆盖完整的测量链路。

操作系统噪声：rtla osnoise

rtla osnoise 用于检测和分析操作系统层面的干扰源。它在用户指定的 CPU 上持续运行密集循环，记录任何打断其执行的因素，包括：

  • IRQs/SoftIRQs：硬件中断和软中断的处理时间。
  • Threads：其他线程抢占当前 CPU 的时间。
  • NMI：不可屏蔽中断的影响。
  • SMI：硬件和固件的执行延迟。

当实时任务出现延迟时，osnoise 数据能帮助确认是否被上述 OS 事件干扰。

调度延迟：rtla timerlat

rtla timerlat 用于测量实时任务从“被定时器唤醒”到“实际在 CPU 上执行”所花费的时间，并将总延迟拆解为两个关键阶段：

  • IRQ Latency（中断延迟）：定时器硬件中断发生后，到内核开始执行该中断处理程序的时间差。此阶段的高延迟通常表示系统存在长时间关闭中断的临界区（如 irq_disable() 区段），或处于 NMI 或 SMI 阶段。
  • Thread Latency（线程延迟）：记录从中断响应（即包含中断延迟），到中断处理程序唤醒实时线程，再到该线程真正被调度并在用户态/内核态执行的时间差值。此阶段的高延迟除了中断延迟外，通常指向唤醒延迟（代码机制本身）、调度器延迟、其他高优先级任务干扰或长时间禁用抢占的代码段。

rtla timerlat 通过记录最大延迟（top）和延迟直方图（hist），直观反映系统的抖动情况。

小结

综上所述，rtla 是一个基于内核机制 FTrace 的白盒工具。它测量延迟与噪声的数值，同时通过内核追踪切片透视延迟的内部结构，为后续的实时优化（如调整隔离 CPU、关中断代码审计）提供直接证据。

rtla背后的内核技术（基于 Linux-6.1 ）

了解 rtla 的用法后，下一步是需要了解一下 rtla osnoise 和 rtla timerlat 背后的内核技术，这样能更熟练地使用 rtla 。

osnoise tracer

参考：https://www.kernel.org/doc/html/v6.13/trace/osnoise-tracer.html

基本原理

rtla osnoise 背后的技术是 osnoise tracer ，它的作用是什么？
它用于测量和分析操作系统噪声。在高性能计算环境中，操作系统噪声指的是由于操作系统内部活动（如中断、线程调度等）或硬件活动（如系统管理中断、陷入比操作系统更高级的 CPU 运行等级），进程造成的运行时干扰。而 osnoise tracer 就是把这些噪音记录起来。它站在一个普通线程的视角，记录下所有可能打断它的“噪音事件”，帮助开发者和系统管理员找出系统性能不稳定的根源。

在 Linux 系统中，一个普通线程在执行过程中会被各种事件打断，例如：

  • NMI：不可屏蔽中断
  • IRQ：硬中断
  • SoftIRQ：软中断
  • Thread：其他线程的抢占
  • HW：硬件噪声，如系统管理中断或虚拟机管理程序的干扰。

设计灵感：OSNOISE Tracer 的设计借鉴了另一个工具 —— hwlat_detector（硬件延迟检测器）。

hwlat_detector 通过禁用中断和抢占，然后不断轮询时间戳计数器来检测硬件或 NMI 引起的延迟。
OSNOISE Tracer 采用了类似的轮询思想，但不会禁用中断和抢占。这使得它可以捕捉到所有类型的操作系统噪声。

工作原理

OSNOISE Tracer 的工作原理可以概括为以下几个步骤：

  • 创建内核线程：它默认为每个 CPU 创建一个内核采样线程（osnoise/CPU），用户也可以自己指定 CPU 。
  • 轮询采样：这个线程在一个运行周期内，一直循环读取时间戳，如 TSC 寄存器，又或者调用 sched_clock() 读取。每次读取之间的时间差（delta），如果它超过 5us（默认设定），就是一次潜在的噪声样本。另外，用户可指定 tracing_thresh ，单位为 ns ，如果噪声样本大于等于 tracing_thresh ，才被确认为噪声。
  • 事件追踪：在轮询之前，OSNOISE 通过调用 osnoise_hook_events() ，在关键的内核事件点（如中断入口/出口、任务切换等）注册了钩子函数。当这些事件发生时，钩子函数会被触发，记录下事件的开始时间、结束时间和类型。

噪声分类：

  • 如果两次轮询之间的时间差超过了预设的阈值（tracing_thresh），就认为发生了一次噪声事件。
  • 此时，OSNOISE 会检查在噪声发生期间，是否有其他被追踪的事件（如 IRQ、NMI）发生。
    • 如果有，则将该噪声归因于对应的事件（例如，一个 IRQ 发生了，噪声就记在 IRQ 头上）。
    • 如果没有任何操作系统级别的事件发生，则判定为硬件噪声（HW）。

输出结果：在每个采样周期结束时，OSNOISE 会输出一份报告，汇总该周期内的噪声情况。

基本原理

Timerlat Tracer 是 Linux 内核提供的一个追踪工具，专门用于帮助开发者定位实时线程的**唤醒延迟（wakeup latency）**来源。它通过在内核中断上下文和线程上下文中分别测量定时器唤醒延迟，将延迟拆分为多个阶段，从而精确定位造成高延迟的根本原因。

Timerlat Tracer 的设计灵感来源于经典的实时延迟测试工具 cyclictest。cyclictest 只能给出一个整体的延迟值，无法告诉开发者延迟具体来自哪个阶段（是中断响应慢？还是线程调度被阻塞？）。Timerlat Tracer 填补了这一空白：

  • 设置一个周期性定时器，定时器到期时触发一个 IRQ，IRQ 处理函数再唤醒一个实时线程。
  • 在 IRQ 上下文 和 线程上下文 分别记录延迟值，并通过 ACTIVATION ID 将两者关联起来。
  • 这样开发者可以一眼看出高延迟是发生在中断处理阶段还是线程调度阶段，进而深入分析。

工作原理

timerlat Tracer 的工作原理可以概括为以下几个步骤：

  1. 在每个 CPU 上创建一个实时优先级为 95 的内核线程（timerlat/CPU），用户也可以自己指定 CPU。
  2. 该线程初始化一个高分辨率定时器（hrtimer），设置一个周期（默认 1ms），用户也可以自己指定周期。
  3. 线程进入睡眠，等待定时器到期。
    • 定时器到期后，硬件触发中断，执行 timerlat_irq 函数（在 IRQ 上下文中）。
    • 记录当前时间与预定到期时间的差值，作为 IRQ Latency（硬中断延迟）。
  4. 唤醒等待的 timerlat 线程。
  5. 线程被调度执行后，再次计算当前时间与预定到期时间的差值（包含：中断响应->中断处理（含线程唤醒）->线程调度->线程执行），作为 Thread Latency（线程延迟）。
  6. 每次激活输出两条记录，通过相同的 ACTIVATION ID 关联。

启用 timerlat tracer 后，读取 trace 文件可以看到类似如下输出：

  • context irq：表示在硬中断上下文中测量的延迟。
  • context thread：表示在线程上下文中测量的延迟。
  • ACTIVATION ID（如 #1）用于关联同一轮激活的 IRQ 和线程记录。

IRQ/Thread 拆分的重要性：

  • IRQ 延迟 可能由硬件相关因素导致：SMI（系统管理中断）、NMI、其他 IRQ、线程屏蔽中断等。
  • Thread 延迟 可能由以下因素导致：其他线程抢占、调度器延迟、中断屏蔽、preempt_disable() 等。
  • 通过拆分，开发者可以快速判断高延迟是来自中断响应慢还是线程调度受阻，从而缩小排查范围。
