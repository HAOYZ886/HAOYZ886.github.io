Linux - 手动注入延迟来观测实时抖动

Posted on 2026-04-25 Edited on 2026-05-03 In 原理及实现 Word count in article: 8.1k Reading time ≈ 30 mins.

前言

根据之前几篇文档的说明可知，RTOS 的确定性来源于项目的需求，而具体的实现是：中断的响应，以及任务的调度和执行完成是否在指定的范围内。
在 Linux 中，

  • 中断的响应快慢，分为以下原因：
    1. 中断是否被关闭（主要），而中断关闭的原因是：
    • 框架/子系统的实现自身要求的，比如 spin_lock_irq()
    • 进入中断上下文（包括 NMI ）时关闭
    1. 硬件延迟（SMI）导致（次要），而导致此的原因是：
    • 如 ARM64 架构，由于 Linux 运行在 EL1 ，则它无法感知 EL2/EL3 ，当陷入更高级运行等级时，内核处于停止状态。
    • 如 X86 架构，BIOS/固件执行相关操作，CPU 无法屏蔽，只能等待完成。
  • 任务的响应快慢，分为以下原因：
    1. 抢占是否被关闭（主要），而抢占关闭的原因是：
    • 框架/子系统的实现自身要求的，比如 spin_lock_irq()
    1. 在就绪队列中的任务，或当前任务的实时优先级比指定调度的任务优先级更高
    2. 实时仲裁（Linux机制，间接导致）。比如在 1 秒时间内要求 0.95 秒跑实时任务，其余时间跑非实时任务。高优先级任务（优先级大于或等于你想要响应的任务）占满 0.95 秒，触发实时仲裁，你想要响应的任务也会被延后至少 0.05 秒得到调度。
    3. 优先级反转。比如低优先级的线程持有锁并正在执行，但是此时高优先级的线程抢占了执行该低优先级的线程的 CPU ，而且尝试获取低优先级的线程已持有的锁，但获取不了从而让出执行权，只能等待低优先级的线程释放锁。
    4. 硬件延迟（SMI）导致

接下来我们分别在中断上下文和进程上下文，手动注入中断与调度延迟，并结合 timerlat、irqsoff 等内核追踪工具，复现并定位 Linux 实时系统中的微秒级抖动瓶颈。

注意：本文不讨论 PREEMPT_RT 补丁的实现原理，也不深入硬件 SMI 优化，重点讲怎么手动构造延迟、怎么用工具观测和定位实时抖动。

为什么要设置 performance 模式？
现代 CPU 默认使用动态调频（如 powersave 或 schedutil），当负载低时会降频休眠。唤醒时 CPU 升频本身就会产生数百微秒的延迟。为了隔离变量，专注于软件逻辑带来的抖动，必须锁定 CPU 最高频率。

宏观观测：使用cyclictest观测

cyclictest 是最经典的延迟测量工具，但它只能告诉你“系统有延迟”，无法告诉你“为什么延迟”。

cyclictest 参数解读：

  • -m: 锁定内存，防止因缺页中断引入额外延迟。
  • –policy=fifo -Sp 99: 使用 SCHED_FIFO 调度策略，优先级设为最高 99。
  • -q: 安静模式，仅在结束时输出统计。

核心参数解读：

  • tracing_thresh: 触发记录的延迟阈值。设为 600000ns，即只有延迟超过 600us 才抓取，过滤噪声。
  • stop_tracing_us: 一旦 IRQ 延迟超过此值立即停止，保留现场，防止高延迟事件被后续覆盖。

我们注入了 1000us，为什么 Max 只有 778us？
这里体现了抢占关闭与中断关闭的重大差异：

  1. 中断未被关闭：硬件定时器准时到来，cyclictest 被即时唤醒（Wakeup），此时时间戳计时已经开始。
  2. 调度被阻止：但由于 CPU 正处于关抢占区间，cyclictest 无法立刻获得 CPU 运行。
  3. 调度延迟波动：cyclictest 实际获得的延迟，取决于定时器中断到来时，那个关抢占的临界区还剩下多少时间没执行完。因此，Max 往往小于注入时间，且数值具有随机波动性。

使用preemptirqsoff追踪延迟点

使用 timerlat 之后，我们基本能定位到抢占关闭的所在位置。当然，我们也能使用 preemptirqsoff 或 preemptoff 来定位问题。
timerlat 是在特定的测量点采样，而 preemptirqsoff 则会记录下从关闭抢占开始，直到重新开启抢占为止这段时间内，CPU 上发生的所有函数调用。

开启 display-graph 选项非常重要，它能让追踪结果以函数调用图的形式展现，层次分明，否则只会看到一维平铺的函数列表。

追踪结果不仅给出了总延迟，还揭示了延迟期间 CPU 的微观活动：

头部信息明确指出，最长延迟（latency: 1001 us）发生在 k_preempt_noise 线程中，始于 preempt_thread_fn（我们的模块入口），终于 return_to_handler（开启抢占的时刻）。

看标志位变化，印证理论：

  • ….1..：最后一列是 preempt-depth（抢占深度）。1 表示当前处于关抢占状态（通常是因为调用了 preempt_disable 或拿了 spinlock）。这贯穿了绝大多数行。
  • d…1.. 到 d..h1..：在 802us 和 913us 时，发生了两次硬件中断。标志位短暂地变成了 h（hardirq），同时 need-resched 标志也被置位（n），说明中断唤醒了高优先级任务。

这完美印证了我们之前的结论：关抢占并不妨碍中断进来，也不妨碍系统在中断里唤醒实时任务，只是实时任务醒来后无法立刻抢回 CPU 控制权。

看耗时拆解：

  • __delay() 函数耗时 1000.125 us，几乎占据了全部延迟。其中包含了两次定时器中断处理的耗时（约几十 us），剩余时间都在“空转”等待。
  • 最后调用 preempt_count_sub 和 tracer_preempt_on，宣告抢占关闭区间结束，追踪结束。

通过线程抢占观测实时抖动

前一节我们探讨了“关闭抢占”，那是系统层面的“锁门”——只要门锁着，谁也别想进来。但在实时系统中，还有一种更隐蔽、更常见的延迟来源：门明明没锁，但门口站着一个“VIP”——高优先级任务正在执行，调度器遵循严格的优先级法则，拒绝让低优先级任务抢占。这就是优先级压制造成的调度延迟。

概念辨析：优先级压制 vs 关闭抢占

  • 关闭抢占：属于代码逻辑主动防护（如持锁）。此时 preempt_depth != 0，调度器被物理禁止进行切换。
  • 优先级压制：属于调度策略被动结果。此时 preempt_depth 可能为 0，系统允许调度，但调度器经过计算发现当前运行的任务优先级更高，于是“合法”地拒绝了低优先级任务的抢占请求。

对于等待被调度的实时任务，这两种情况的体感是一样的，就是都等不到 CPU ；但在追踪工具的显微镜下，它们的机理截然不同。

以下实践指定使用 CPU6 为例，读者根据自己的实践环境修改。

环境准备

为了模拟高优先级 VIP 霸占 CPU，我们需要做两件事：一是赋予噪声线程最高的实时优先级；二是解除内核对 RT 任务的限流保护。

继续沿用内核模块 preempt_noise 进行测试：

为什么要修改 sched_rt_runtime_us？
Linux 内核默认开启了 RT 任务的 CPU 带宽限制（sched_rt_runtime_us 默认通常为 0.95s，而周期 sched_rt_period_us 为 1s）。这意味着在 1 秒的周期内，所有 RT 任务最多只能运行 0.95 秒，剩下的 0.05 秒必须留给普通任务，以防失控的 RT 任务锁死系统。
在我们的实验中，如果不设为 -1 取消限制，当高优先级的噪声线程持续霸占 CPU 一段时间后，内核会强行将其挂起。这种“被内核惩罚”的挂起会干扰我们对“纯粹优先级压制”的观测，因此必须解除枷锁。

  1. 看 IRQ Latency：irq timer_latency 942 ns，极短！再次证明中断响应毫无阻碍。
  2. 看 Thread Latency：thread timer_latency 140062 ns（约 140us），又飙升了！

  5. 细节补充：你可能注意到 preempt-depth 为 3（d…3..），这不是因为我们手动关了抢占，而是因为 ftrace 自身在追踪时会产生嵌套的 preempt_disable，但这只是观测带来的副作用，并不影响高优先级压制低优先级的本质逻辑。

总结

本节演示的场景，在实际的实时应用开发中相当常见。很多开发者以为给任务打上 SCHED_FIFO 并赋高优先级就没事了，却忽视了该任务内部是否存在长耗时循环或 udelay。

在 PREEMPT_RT 内核中，大部分硬中断都被线程化了，它们也受调度器管辖，有了优先级。 如果你的高优先级业务线程出现 Bug（如死循环、长时间轮询寄存器），不仅会饿死同 CPU 上的其他普通任务，甚至可能压制中断线程，导致系统看上去像“关了中断”一样卡死。这也是为什么在使用实时调度策略时，必须配合严格的代码审查与 Watchdog 机制。

硬件延迟

在前面的章节中，无论是硬中断风暴、调度延迟还是关闭抢占，它们都有一个共同点：罪魁祸首都在 Linux 内核的管辖范围内，因此 Ftrace 能够忠实地记录下它们的“作案过程”。
然而，实时开发中最令人绝望的场景往往发生在内核视线之外：系统明明没有高负载，Ftrace 报告也干干净净，但 cyclictest 却测出了毫无规律的毫秒级抖动。这就是所谓的“硬件黑洞”。

原理：消失的时间去哪了？

对于ARM64架构

在 ARM64 架构中，特权级分层非常严格：

  • EL0：用户态应用程序。
  • EL1：Linux 内核。
  • EL2：虚拟化层。
  • EL3：安全固件层。

当内核正常执行时，它处于 EL1。但如果发生系统调用（陷入 EL2 Hypervisor）或安全服务调用（SMI 陷入 EL3 ATF），CPU 的控制权会暂时脱离 Linux 内核。在这段时间内：

  • 内核完全冻结：时钟中断无法响应，调度器停滞。
  • Ftrace 失效：因为内核代码都没跑，追踪点自然无法触发。
  • 现象：Trace 日志中会出现一段空白，紧接着发生时间戳的剧烈跳变。

这就好比有人把监控室的录像机暂停了半小时，虽然录像带上看起来风平浪静，但外面的世界其实已经发生了翻天覆地的变化。

对于X86架构

在 x86 平台上，这种黑洞有一个具体的名字：SMI（System Management Interrupt）。它是 x86 架构实时性优化的“头号公敌”。
x86 架构不仅有我们熟悉的 Ring 0（内核）和 Ring 3（用户态），还有更底层的 Ring -1 和 Ring -2。SMI 运行在 Ring -2 的 SMM（System Management Mode） 模式下。

当 SMI 发生时：

  1. 接管一切：CPU 暂停当前所有任务（包括 Linux 内核），保存状态后进入 SMM 模式。
  2. 完全不可见：操作系统对此毫不知情。在 Linux 看来，CPU 就像“丢失了”一段时间片。
  3. 用途广泛：BIOS 厂商通常利用 SMI 来处理风扇转速控制、温度监控、电源管理等“关键任务”。

虽然 SMI 对系统稳定性很重要，但对实时性来说却是灾难。

  • 不可阻塞：SMI 的优先级高于任何操作系统中断。Linux 内核无法屏蔽它，必须等待其执行完毕。
  • 耗时不确定：如果 BIOS 编写不当，某些 SMI 处理例程（如复杂的风扇调速逻辑）可能耗时长达数毫秒。对于微秒级敏感的实时应用，这简直是毁灭性的打击。

在Realtime KVM指出：“SMIs for x86 take care of things such as fan speed… SMIs cannot be blocked by the operating system and can take up to milliseconds to run in extreme cases. During this time, the operating system is completely blocked from running.”

总结

回顾本文的实践，实时延迟排查可以按四个层次推进：

  1. 第一层：应用感知 │ 工具：cyclictest, rt-tests
    • 发现问题：P99延迟超标、周期抖动
  2. 第二层：分类定责 │ 工具：timerlat, function_graph
    • 区分：中断响应延迟 vs 调度延迟
    • 关键指标：IRQ Latency、Thread Latency
  3. 第三层：代码定位 │ 工具：preemptirqsoff, irqsoff
    • 定位：关中断、关抢占的持锁路径
    • 典型场景：自旋锁持有时长、中断屏蔽
  4. 第四层：硬件探测 │ 工具：hwlatdetect
    • 硬件黑洞：SMI（x86）、ATF/TrustZone（ARM）
    • 固件陷阱：BIOS配置、节能特性

Linux 实时延迟的常见来源，整理如下：

延迟类型 根本原因 典型场景 排查工具
中断阻塞 中断被屏蔽（local_irq_disable） 驱动持锁关中断、长时间ISR irqsoff, timerlat
抢占阻塞 抢占被禁止（preempt_disable） 自旋锁持有、RCU读临界区 preemptoff, preemptirqsoff
调度延迟 高优先级任务占用CPU SCHED_FIFO任务死循环、优先级反转 timerlat, sched_switch事件

实时性排查没有银弹。上面这些工具和方法，从不同维度逼近同一个目标：搞清楚那几毫秒到底花在了哪里。本文只是模拟现象去使用各自工具去排查实时抖动，但在实际环境中，很多问题都是环环相扣的，又或者说输出的报错信息只是一个表象，根源还得经过层层解剖才能得知。所以说，在当今 AI 时代，解决问题永远是需要具备基础原理和实践经验，还有一把趁手的工具。
