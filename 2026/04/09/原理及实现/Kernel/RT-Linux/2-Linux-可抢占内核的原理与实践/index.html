Linux-可抢占内核的原理与实践

Posted on 2026-04-09 Edited on 2026-04-11 In 原理及实现 Word count in article: 4.9k Reading time ≈ 18 mins.

可抢占内核和非可抢占内核是什么

可抢占内核与非可抢占内核的区别在于内核态代码是否允许被强制打断，这直接影响系统在低延迟响应与高吞吐量之间的取舍。

定义与典型场景

  1. 非可抢占内核
    • 当一个进程因系统调用或中断进入内核态运行时，该进程独占 CPU 直至内核态执行完毕（返回用户态）、主动调用调度器让出 CPU，或在显式的抢占点检查调度。即使有更高优先级的就绪任务，也无法抢占当前内核态任务的执行权。
    • 典型场景：服务器、高性能计算集群。这些场景更关注单位时间内处理的任务总量（吞吐量），而非单个任务的响应延迟。
  2. 可抢占内核
    • 内核态代码执行路径中，除了持有自旋锁或显式禁用抢占的极短临界区外，均可被高优先级任务强制打断。调度器可以随时剥夺当前内核态任务的执行权，切换至更高优先级的任务。
    • 典型场景：桌面系统、软实时嵌入式系统、多媒体处理。这些场景要求系统对交互事件或外部中断有较快的响应速度，即使牺牲部分吞吐量。

更深层的对比

非可抢占与可抢占内核并非简单的二选一，而是两种不同的设计哲学，体现在以下维度：

对比维度 非可抢占内核 可抢占内核
调度延迟 无界：延迟取决于内核态代码执行时长，可能达到数百毫秒 有界：延迟极短且可预测，通常在微秒至毫秒级
吞吐量 高：更少的上下文切换与缓存失效，CPU 时间更多用于实际计算 相对较低：频繁的抢占带来上下文切换开销，影响 Cache/Pipeline 性能
锁机制复杂度 低：内核态天然串行，对自旋锁等保护机制的要求较弱 高：必须使用 preempt_disable() 或自旋锁严格保护临界区，防止并发导致数据损坏
设计目标 让 CPU 尽可能多地执行计算任务 让高优先级任务尽可能快地得到响应

延迟的根源：抢占点分布差异

内核通过设置 TIF_NEED_RESCHED 标志位来表示需要调度，但”何时检查该标志位”决定了抢占模式：

  • 非可抢占内核：仅在返回用户态前夕（如系统调用返回、中断返回用户态）检查标志位。如果低优先级任务陷入一个耗时 5 秒的系统调用，高优先级任务即使被唤醒，也必须等待这 5 秒。
  • 可抢占内核：在返回内核态前夕（如中断返回内核态）、释放自旋锁时（preempt_enable）以及显式抢占点（cond_resched）都会检查标志位。条件满足则立即触发调度。

吞吐量的代价：上下文切换与缓存惩罚

  • 非可抢占内核：内核态执行流不被打断，指令流水线和 CPU 缓存（Cache）能保持高命中率，硬件预取也能高效工作，从而实现高吞吐量。
  • 可抢占内核：频繁的抢占导致 CPU 不得不保存/恢复寄存器状态（上下文切换），且新任务可能访问不同的内存区域，导致 Cache 大面积失效。这种”缓存颠簸”直接损耗了 CPU 的有效计算时间。

实现复杂度：临界区的保护

在非可抢占内核中，由于内核态本身不可被调度，内核代码在一定程度上天然避免了并发冲突。但在可抢占内核中，任何可能被抢占的代码路径如果访问共享数据，都必须通过禁用抢占（preempt_disable）或加锁来保护。

实时抢占内核

选择配置：CONFIG_PREEMPT_RT

相比普通抢占内核，PREEMPT_RT 进一步扩大了可抢占的范围，绝大部分内核代码都可以被抢占。主要改动包括：

  1. 将大部分自旋锁替换为可抢占的实时互斥锁（rt_mutex），使得持有锁的代码路径也能被抢占。
  2. 将硬中断处理程序（ISR）线程化，在进程上下文中以内核线程的形式执行。不同中断可配置不同的实时优先级（默认通常为 50），使得中断处理也能参与调度和抢占。
  3. 将软中断的处理移至 ksoftirqd 内核线程的进程上下文中执行，避免在任意上下文中长时间关闭抢占。
  4. 采用高精度定时器，提供更精确的时间管理。

运行结果：

thread2 在内核态执行期间，thread1 于第 3 秒醒来。此时内核检查 preempt_count 为 0 且 TIF_NEED_RESCHED 被设置，立即触发抢占，无需等待 mdelay 结束或显式抢占点。thread1 准时在第 3 秒恢复运行。

使用 ftrace 的观测：

注意第 36 行，在 sched_wakeup 期间，处于硬中断上下文，thread2 的 TIF_NEED_RESCHED 标志位被置位。结合可抢占内核的特性，在中断返回期间 thread1 得到 CPU 的执行权。

注意第 36~37 行，sched_wakeup 与 sched_switch 的时间差仅为微秒级（43962.851809 - 43962.851796 ≈ 3μs），实时抢占有更快的响应能力。

总结

从实践结果看，从任务切换的抖动延迟来说，不同的抢占策略，高优先级线程的抢占延迟也不同。如果采用实时抢占内核，高优先级的任务能够更快地得到执行。
但是，”更快”并不代表实时抢占内核就是硬实时内核，实时抢占内核只是提供了尽可能达到硬实时的内核基础。因为实时操作系统的核心特性是确定性，而确定性是由使用场景和需求决定，且最终应用到整个操作系统（包含驱动、中间层和应用程序），并非仅用一个内核来决定的。
