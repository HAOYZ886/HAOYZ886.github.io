Linux - 深入理解DRM

Posted on 2025-05-28 Edited on 2026-03-14 In 原理及实现 Word count in article: 59k Reading time ≈ 3:34

DEBUG

如果想要用 DRM DEBUG ，首先要确保当前内核的打印等级是否为 KERN_DEBUG ，如果不是则不能使用 DRM DEBUG 。
在 DEM DEBUG 中，额外设置了独属于它自己的打印等级，声明在 enum drm_debug_category from include/drm/drm_print.h 。里面说明了该 enum 如何使用。在 drm_print.h 内定义了一系列名为 DRM_DEBUG_XXX() 的宏，而且这些宏的核心函数是 __drm_dbg() -> ___drm_dbg() ，其中 ___drm_dbg() 定义在 drivers/gpu/drm/drm_print.c 。
另外，还有定义了一系列名为 drm_dbg_xxx() 宏，和 DRM_DEBUG_XXX() 不同的是，它额外需要 drm_device->dev 来显示当前要显示的设备名，如 IMX8MP 的 display-subsystem 。这一系列宏的核心函数是 drm_dev_dbg() -> __drm_dev_dbg() 。

DRM框架的预先初始化

在 DRM 驱动初始化前，需要先调用 drm_core_init() ，做一些准备工作。
DRM 有一个内核参数，名为 nomodeset ，作用是把 DRM 关闭。所以在 DRM 驱动的初始化的第一步，就是检查 DRM 是否被关闭了，可调用 drm_firmware_drivers_only() 去检查。

在设备树中表示的结构分布

在 DRM 框架中，有一个整体的操作对象 drm_device ，它包含当前平台的一个显示模块（包含 LCDIF 、PHY 和 Panel 等固件/外设），以及显存。

显示模块对应 KMS 框架、显存对应 GEM 框架。

一个平台的一个基于DRM框架显示模块在设备树中的表示

DRM 框架就像面向对象中的类 Class ，那 DRM Driver 就像面向对象中的 Object 。

又或者说，Linux 中的大部分驱动子系统亦是如此。

能让 DRM Driver 运行起来，必然需要资源信息来支撑，而设备树就是这些资源信息的载体。DRM 框架有自己一套表示一个显示模块的框架，它利用 aggregate-component 机制，把 LCDIF 、PHY 和 Panel 等固件/外设连接起来，而且还有一个中心节点，它是当前显示模块的“灵魂”。
在 IMX8MP 中，它的内核设备树当中存在一个名为 display-subsystem 的节点，它就是当前平台的一个显示模块的主角。

同时，它的属性 ports 指向了当前平台的所有 LCDIF 。
也可以说 display-subsystem 是当前平台的 DRM driver 的真正起点，没了它没法走到 DRM driver 初始化的下一阶段（见基于DRM框架显示模块的设备树结构的解析）。

GPU 驱动也使用 DRM 框架，GPU 也是一个平台的一个显示模块，但 GPU 驱动过于复杂，无法细究。

We have lots of these. And the cleanup code tends to be of dubious quality. The biggest wrong pattern is that developers use devm_, which ties the release action to the underlying struct device, whereas all the userspace visible stuff attached to a drm_device can long outlive that one (e.g. after a hotunplug while userspace has open files and mmap’ed buffers). 仅靠以上解释是很难理解用途的，需要一个实例才能理解，而且这个和 struct drm_device 的字段 kref 和 unplugged 有关系。

  • kref ：引用计数，记录 drm_device 被引用的次数
  • unplugged ：数据类型为 bool ，当 drm_device 对应的物理设备被拔出后，被置为 True 。

这里先去掉 drmm 、kref 和 unplugged 的功能，资源的管理是用 struct device 的 devres 功能。目的是为了能够清晰理解这三个功能的作用，和它们之间的关系。

假设该设备被拔出，则会发出硬件中断，假设该中断处理程序对该情况的处理是：移除 pci_dev ，则执行以下操作：

struct pci_dev 内有 struct device ，当移除 pci_dev 时，也会把 struct device 的 devres_head 记录的资源释放。
此时出现一个问题，假设拔出之前某一个应用进程已打开 /dev/dri/cardX 来访问 drm_device ，因为 drm_device 等描述符已被释放，如果还通过系统调用去访问，后果不堪设想。而且见 drm_file_free() 可知，关闭一个文件时，需要 drm_device 来参与，如果此前 drm_device 就“消失”了，这不对吧？此时应该把这些资源的生命周期，延长到该应用进程关闭 /dev/dri/cardX 后。最起码要让应用进程知道 /dev/dri/cardX 对应的物理设备已被拔出，提前关闭访问。
还有一个情况，就是 atomic_commit 期间。已知在 atomic mode 下的任何操作都不能被打断，但是“拔出设备”期间的 struct device 的 devres 释放操作影响了 atomic mode ，一切都变得不确定性。

基于以上情况，

  • drmm 机制的作用就体现出来了，把资源集中到它这边。这样在如 pci_dev 释放期间释放 struct device ，drm_device 等资源不会受此影响。
  • 用 unplugged 表示当前 drm_device 是否处于拔出状态，如 drm_open() 、drm_gem_mmap() 和 drm_ioctl() 等用 drm_dev_is_unplugged() 查询当前 drm_device 是否处于拔出状态。如果处于拔出状态则直接返回 -ENODEV 错误码。
  • 用 kref 记录当前 drm_device 的引用状态。每次进行 atomic_commit 前，或打开 /dev/dri/cardX 时，当前 drm_device->kref 加一。引用计数为 0 ，则释放 drmm 记录的资源。如 drm_open() ，查询到当前 drm_device 处于 unplugged 状态，则计数减一，如果此时为零，则释放 drmm 资源。

总结

见 drmm 、unplug(不仅仅是 drm_device->unplugged，而是全部与 unplug 有关的) 和 kref 的依赖：

  • drmm -> kref ：当 kref 为零时，释放 drmm 内登记的资源
  • unplug -> kref ：初始化并登记 drm_device 时，起始 kref 为 1（见 drm_dev_init() ），注销 drm_device 时，kref 减 1（见 devm_drm_dev_init() 的 devm_drm_dev_init_release() ）。可以说只要不注销 drm_device ，kref 只会大于等于 1 ，所以“注销 drm_device ”才是释放 drmm 资源的关键点。
  • unplug -> drmm ：它们是间接关系，它们之间关系是通过 kref 建立的。

总得来说，这个机制是当当前 drm_device 被拔出后：

  • 让应用进程知道当前打开的 /dev/dri/cardX 已被拔出。
  • 让当前 atomic_commit 正常执行。毕竟最终面向的操作对象是硬件，对应的 DRM Driver 也需有相关的操作来处理当前 atomic_commit 。这是因为诸如 crtc 、encoder 和 connector 等是 DRM Driver 的基础对象，这些基础对象的上层对象会有相关的状态标志，对当前 atomic_commit 做处理。

那么这些易变的属性值会存储到哪里？
存储在各个组件的 struct drm_xxx_state 当中，如 struct drm_plane_state 、struct drm_crtc_state 和 struct drm_crtc_state 等。在进行 ATOMIC 操作时，会使用 struct drm_atomic_state ，这些组件的 struct drm_xxx_state，集中在这个事务型结构体。如果 ATOMIC 操作成功，会在各组件对应的描述符中，指向新的 struct drm_xxx_state 。如 struct drm_plane 的字段 state 指向 new_state 。

为什么要把易变的属性存储到 struct drm_xxx_state 当中？

建议先看 ATOMIC—MODE

倒不如想想为什么需要 struct drm_xxx_state ？该结构体的出现是因为一个理念：“每一帧都是完美的” 。众所周知，想要完美是很难的，要么不做，那么就一定要做到完美。而且这和 Atomic Mode 理念一致，Atomic Mode 就是中途不能出错，一出错就回退之前的状态,不能有中间过程。
如果给一个屏幕更换显示模式，对应驱动必然要“动员”对应的所有组件去操作（利用 struct drm_atomic_state ）。但是中途失败了怎么办？中途所设置的属性状态，必然要回退到操作前的状态。如果失败了就摆手不干了，那么以后的显示操作都在这个错误中执行，一步错，步步错，这也违背了 Atomic Mode 理念。
根据 ATOMIC-MODE 可知，display pipeline(s) 的搭建由 struct drm_atomic_state 和各组件（除 Encoder ）的 struct drm_xxx_state 主导。在 ATOMIC 操作中，分为 ATOMIC CHECK 阶段和 ATOMIC COMMIT 阶段，仅允许 ATOMIC CHECK 阶段报错时回退，ATOMIC COMMIT 不能报错（除非硬件的致命错误和系统报错）。而且回退并不是字面意思，而是检测到 new_state 出错时，仅把 new_state 移除，让当前组件继续应用 old_state 即可。其中 old_state 和 new_state 的本体是各组件（除 drm_encoder ）的 drm_xxx_state ，如 drm_connector_state 。它们的记录了组件需要的属性值，以及组件之间的连接。
而且 drm_atomic_state 是带有“请求”的意思，即它是事务型结构体，与组件描述符对应的结构体不同。在 ATOMIC 操作过程中，它是带有“实时性” ，即仅在当前请求/回应时处理有效，且当前是处于最新的。还有，drm_xxx_state 具备 “时效性”，即 ATOMIC 操作成功后，会存储此 state ，并以此继续执行后续操作，一直到有新的请求，会把它继承给新的 state 。
另外，由于把属性值存储在 struct drm_xxx_state 当中，那么意思就是说会有很多的 struct drm_atomic_state ，可以进行批量操作，在不同的原子操作之间重用相同的 struct drm_object_properties，提高了 “灵活性” 。而且每个 drm_atomic_state 都是独立的，且有互斥保护。
通过以上的说明，显而易见，把易变的属性存储到 struct drm_xxx_state 当中是很恰当的，方便以组件的 drm_xxx_state 为单位去更新属性。

funcs和helper_funcs之间的不同

各个组件都分别有 funcs 和 helper_funcs 字段，它们之间最主要的区别：

  • funcs 以自身为主导，不会干涉和影响其它组件，注重于当前组件的使用，但更多注重于 DRM 框架的操作，如 drm_atomic_helper ，并非仅仅是组件对应的硬件操作。
  • helper_funcs 是为了当前主操作为辅，这个主操作不仅包含当前组件，还有其它的组件。如主操作 atomic commit ，为了使以当前 connector 为终，以当前 CRTC 为始的 pipeline 路线使能，需要给沿路的组件使能。这些组件的使能操作就是在 helper_funcs ，都是 atomic commit 的一部分，而且是每一个都不可或缺的。

DRM 框架中有很多机制，为了让开发者快速上手开发，把这些机制尽可能地按主要功能做封装，如 drm_probe_helper.c 和 drm_atomic_helper.c 内的函数定义，它们的函数名都有 helper 的都是封装好的。这些源码文件内的函数相当于就是给驱动开发者使用 DRM 框架的“标准用法”，同时具备通用性，可理解为框架级 helper 。它们对 helper 的概念和组件中的 helper_funcs 的不一样，而是把一个机制封装好作为标准，可以作为某个主操作的一部分，也可作为主操作。另外，有些框架级 helper 需要涉及到组件的 helper_funcs ，如 drm_atomic_helper_commit、drm_atomic_helper_commit_modeset_disables/enables() 等。

关键区别

类别组件 组件 funcs 组件 helper_funcs 框架级 Helper
作用域 组件自身操作 跨组件协作操作 通用机制封装（如 Atomic 提交流程）
调用者 直接由驱动或框架触发 由框架级 Helper 触发 由驱动或框架直接调用
依赖关系 独立或与硬件直接交互 依赖其他组件的状态 可能依赖组件 helper_funcs

特点

  • funcs：定义组件的“能力”（Can-do），即它能做什么。
  • helper_funcs：定义组件的“协作规则”（How-to），即它如何与其他组件配合。
  • 框架 Helper：提供“标准答案”，开发者只需填空（Fill in the blanks），无需重新发明轮子。

为什么需要Plane

从硬件的角度出发，plane 和 CRTC 在硬件的角度来说是一体的，对应的硬件是 LCD Controller ，在 IMX8MP ，对应的硬件是 LCDIF 。
LCD Controller 的最基础作用是在指定的内存中读取像素数据，并把数据传输到目标屏幕上。在此之前还需要相关配置，如分辨率、消隐区、像素时钟、像素格式和 pitch 等。
这时就把 LCD Controller 的一个功能，把图层功能抽象出来，这个图层包含：目标屏幕上的 XY 轴坐标和图像大小，以及显存地址等。这个显存也得根据分辨率、像素格式和 pitch 生成。而 DRM 的 Plane 功能，仅关注“我该如何去使用显存”，并不管理显存。Plane 对应的描述符 drm_plane ，有指向一个 drm_framebuffer ，这个可以理解为它是 Plane 的 “对象” ，而 Plane 是 “Class” 。为什么需要这样理解？
这个需要结合硬件理解。前文说过，Plane 只管去使用，以 imx8mp 为例，它的 lcdifv3 有一系列的寄存器来表示它的 Primary Plane ： CTRLDESCL0_1~5 。下面简略说明它们的作用：

  • CTRLDESCL0_1：设置分辨率
  • CTRLDESCL0_3：设置 pitch ，说明一个像素的深度，如 bpp32
  • CTRLDESCL0_4：设置显存基地址
  • CTRLDESCL0_5：设置像素格式，以及使能当前 plane

以上属性组成 “class” ，称为 plane ，然后你使用这个 “类” 新建出一个实例化对象，称之为 drm_framebuffer 。创建这个对象你需要输入分辨率、pitch、显存基地址和像素格式。基于以上理论延伸，也可以理解为 drm_framebuffer 也是只管“我如何去使用显存”。同时它也是 KMS 与 GEM 的桥梁，它指向 drm_gem_object ，但并不管理显存。
drm_gem_object 是 GEM 的基础对象，把显存抽象为对象。这样做的原因是显存是各种各样，可大致分为两类：

  • 类型为 dumb 的显存，把 CPU 的内存当作显存，可使用 CPU 或 DMA 搬运数据到显存。
  • 类型为 smart 的显存，独立于 GPU 的显存，由 GPU 处理，无需 CPU 。

还有按 Linux 内核，以及结合以上两个大类，按功能，可大致细分为：

  • 基于 DMA 内存分配器的显存，名为 drm_gem_dma_object
  • 基于 shmem 的显存，名为 drm_gem_shmem_object
  • GPU 的显存 VRAM ，名为 drm_gem_vram_object

以上三个 drm_gem_*_object 都是基于 drm_gem_object 。这些 object 才是真正管理显存，可直接对应显存。而 drm_gem_object 就是一个“骨架”。
以上内容均是 GEM 的概念，详细看 GEM 。

Plane 对应的描述符 drm_plane 存在字段 format_types、format_count 和 format_default ，它们的作用是当前的 Plane 支持哪些像素格式。
当然，以上的理解是基于基础功能来举例的。实际上，硬件功能的不同，支持 Plane 的程度也不同，比如说一个LCD Controller 支持多个显存，则在 DRM 中可表示为一个 CRTC 对应一个主 Plane 、一个光标 Plane 和一到多个叠加 Plane 。这些 Plane 会被 CRTC 整合在一起输出到屏幕。另外，一个 Plane 对应的 Framebuffer 根据像素格式的不同，也会有多个显存对应，虽然说在 Plane 眼里是一个整体，但是 CRTC 会把多个显存整合在一起为一个图层。

为什么需要Encoder

Encoder 从字面意思理解，就是把获取到的像素信号，转换为显示屏规定的像素信号再输出。 CRTC 连接着 Encoder ，对应的硬件分别是 LCD Controller ，而 Encoder 可以是 LVDS 、MIPI-DSI 和 HDMI 等。CRTC 输出的像素信号是“原始”的，这里的“原始”是指它自己本身支持的像素格式，但是传输到 Encoder 后，Encoder 还需要对此数据做转换，才能把数据传输到屏幕（被 Connector 描述）。比如 LVDS ，LVDS 的像素格式分为两大类，分别是 SPWG 和 JEIDA 。LCD Controller 把数据传输到 LDB（LVDS Display Bridge）后，根据 LVDS 屏幕要求的像素格式，把“原始”的像素信号在 LDB 转换后再传输到 Panel 。

再举个例子，一个 Encoder 对应 MIPI-DSI Controller，Connector 是 MIPI-DSI 屏幕。把像素信号从 LCD Controller 发送到 MIPI-DSI Controller，该模块接收到并把它编码为符合 MIPI-DSI 的标准的像素信号，发送到 Connector 。

相同特性的 Encoder ，为什么用 drm_encoder 或 drm_bridge 去表示？
一个主要区别是 drm_encoder 是固定的，是作为 display pipeline 的主要节点，对应硬件中处于固定且必要的位置（比如说内置在 SoC 内）。drm_bridge 是相对灵活的，不受平台约束，仅关注自身实现，但必须根据硬件布局与 drm_encoder 联系。
结构体 drm_encoder 存在一个字段 bridge_chain ，从中得知一个 drm_encoder 具备管理 drm_bridge(s) 的功能。
drm_bridge 的功能和 drm_ncoder 一样，但 drm_bridge 出现的原因是为了应对硬件的复杂变化（灵活性高）。另外，还能封装为一个 Encoder 的实例。

这里可以理解为 drm_encoder 具备操作硬件的功能，比如说实现了对应的 callback 函数 .atomic_enable() 和 .atomic_disable() 等。而 drm_bridge 呢？它把 drm_encoder 或上一个 drm_bridge 输出的像素数据编码为它自己的特定格式输出到下一个 drm_bridge 或 drm_connector（目标屏幕）。

为什么需要drm_panel

drm_panel 通常用在嵌入式领域。假设没有 drm_panel ，以 DRM 常规的 display pipeline 来说，适配一块屏幕前，先确认 Encoder 是否有对应的驱动实现。该驱动需要用到 drm_encoder 来描述 Encoder ，控制像素信号的传输。另外，Encoder 驱动内还包含 drm_connector ，表示如何获取显示参数。但这个实现由 SoC 厂商决定，也可以另起一个文件来实现 Connector 驱动（屏幕驱动），但也无法保证这个 Connector 驱动是通用的。
对于嵌入式领域，常用到的屏幕有 LVDS 、MIPI-DSI 和 RGB 等，它们一般不具备热插拔功能，没有额外的 ROM 存储 EDID 。它们一般用设备树节点 panel 去描述它们各自的时序、像素格式和传输方式等。另外，还要用到 PWM 背光、额外的电压控制和复位等等。这些功能在 Encoder 驱动中实现，导致耦合度极高。
比如说，drm_encoder 的回调函数 .atomic_enable() 和 .atomic_disable() 的内部实现已包含 Encoder 本身的硬件操作，如果还要额外加上屏幕的操作，比如上电、开启或关闭背光等，这也导致耦合度极高。另外，根据 为什么需要Encoder 可知，drm_encoder 有 bridge_chain ，从硬件角度来说，输出端连接的未必就是屏幕（drm_connector），也可以是下一个 Encoder 。那么在 drm_encoder 实现的对屏幕操作就显得冗余了。急需需要用一个结构体来描述 Panel 。
如果没有 drm_panel ，客户适配一个屏幕会有一定难度的，因为 SoC 厂商提供的 Connector 未必就是通用的。而且屏幕硬件的特性也是多样的，未必就在 SoC 厂商的适配范围内。同时屏幕厂商也会头痛，因为没有好的方法让客户快速移植并适配屏幕。
如果没有 drm_panel ，则屏幕厂商用 drm_connector 实现屏幕驱动，但 drm_connector 的定位是检测连接状态和获取显示参数。在 display pipeline 中，只能存在一个 Encoder ，而且还不好获取并与之 attach（调用 drm_connector_attach_encoder()），因为每个平台对 drm_encoder 的封装是不一样的（drm_encoder 作驱动的 base object）。而且还不好改动 drm_encoder 的回调函数，如 .atomic_enable() 和 .atomic_disable() ，与他们的屏幕的开启/关闭操作之间联系。当然，也能用 drm_bridge + drm_connector 过渡，但 drm_bridge 的定位并不与之相符。
如果有 drm_panel ，可以另起一个驱动来描述它。在目录 $KERNEL/drivers/gpu/drm/panel 中，里面有各自厂商的 Panel(s) 驱动，移植难度大大降低。其中体现出了独立性和灵活性，仅关注自身实现，不依赖于平台。使得它和 drm_bridge 有着异曲同工之妙。

回顾 为什么需要drm_panel ， drm_panel 的作用是把独属于 panel 的操作从 drm_encoder 和 drm_connector 解耦。这里也产生了一个问题，就是 drm_panel 的回调函数集 drm_panel_funcs ，诸如 .enable() 、.disable() 和 .get_modes() 等回调函数，到头来也还是由 drm_encoder 和 drm_connector 所属的 Encoder 驱动来调用它们。所以说，drm_panel 仅解决了把功能操作抽出来了，并未解决由谁来调用它。尤其是对于 drm_encoder ，它管理着 bridge_chain ，还让 drm_encoder 驱动去调用 drm_panel 的回调函数，这不太合理，还没从根本上做到高内聚低耦合。因为 panel 的输入端是上一个 Encoder ，如果不是 drm_encoder ，而是 drm_encoder 的 bridge_chain 的最后一个 drm_bridge 。如果让 drm_encoder 去操作 drm_panel ，使得整条 display pipeline 的操作顺序改变。比如说使能操作，变为先是 drm_encoder 和 drm_panel 使能，后面到 bridge_chain 的 drm_bridge 使能，这不合理。如果把 panel 的调用操作放到 bridge_chain 的最后一个 drm_bridge ，如果是开发者自己写的 drm_panel 和 drm_bridge 的配套驱动还好说，但如果不是呢，这也从中增加了开发成本，还是具有一定的耦合度。就是要修改 drm_bridge 驱动，尤其是修改它的 .enable() 和 .disable() ，分别增加 drm_panel 的调用 callback 函数 .enable() 和 .disable() 。
所以回顾上图，这里新增一个 drm_bridge ，它的 drm_bridge_funcs 的 .enable() 和 .disable() ，分别调用 drm_panel 的回调函数 .enable() 和 .disable() 。换而言之就是在 drm_encoder 或 bridge_chain 的最后一个 drm_bridge ，和 drm_panel 之间增加了一个无任何硬件修饰的 drm_bridge 作为 “中间层” 。这使得无需过多修改自身的 drm_encoder 或 drm_bridge 驱动去适配 drm_panel 。

另外在 DRM 框架，通常调用 drm_helper_probe_single_connector_modes() 获取目标屏幕的显示参数，而使用的对象是 drm_connector ，该函数会调用drm_connector_helper_funcs->get_modes() 获取显示参数。那么要怎么从 panel 获取到显示参数？
在 Linux 嵌入式领域，通常来说 DRM 框架中的 Panel 常用于嵌入式。对于哪些没有从屏幕获取显示参数特性（EDID）的屏幕来说，如 LVDS 和 MIPI-DSI ，仅能在设备树中用一个节点表示一个屏幕 panel 的显示参数，如最基本的时序、屏幕的特性和输出的像素格式等，额外的还有背光、使能控制和复位控制等。
如果想通过调用 drm_helper_probe_single_connector_modes() 获取屏幕的显示参数，可以在 Connector 驱动中，在初始化阶段查找并记录 drm_panel ，使得 drm_connector 与对应的 drm_panel 在驱动层面上的绑定（根据实际的硬件布局），然后调用 drm_helper_probe_single_connector_modes() 时，调用当前 drm_connector 的 .get_modes() ，在此 callback 函数的代码实现中，找到与之绑定的 panel ，调用 drm_panel_get_modes() 获取来自 panel 的显示参数。
但上文讲过，在 drm_connector 添加与 drm_panel 有关的操作，无疑这还未根本上移除 drm_connector 与 drm_panel 之间的耦合度。
另外，根据 为什么需要Encoder 可知，如果当前的 drm_bridge 是 bridge-chain 的尾部，则它下一个连接的就是 drm_connector，那么在 drm_bridge 驱动中，是否可以由它来创建 connector ？当然是可行的。drm_connector 表示一个屏幕，定位是用于检测显示屏的连接状态（包括热插拔）、获取显示参数（包含 EDID），不具备使能的能力。则结合上文提到的“中间层” drm_bridge ，由它来新建一个 drm_connector 。该 drm_connector 的 .get_modes() 实现为调用 drm_panel 的 .get_modes() 。这样也不用 Encoder 驱动去实现 drm_connector ，降低开发难度。
结合以上的机制，就实现出了 panel_bridge 。

ATOMIC-MODE

概述

ATOMIC-MODE 正如其名，它是带有原子性的操作模式。
先理解原子性是什么，然后再来理解 ATOMIC-MODE 。
原子性是一个不可分割的整体，一个整体包含一组可被检查和应用的对象，它被视为原子事务或原子操作。
原子性遵循完整性，要么有，要么无，不能仅完成一部分。而且执行过程中出现错误时，必须回滚到执行前的状态，不能出现中间状态。

原子性的具体应用及实践（DRM的应用）：
根据原子性的特性，在执行原子性操作前，必须对该操作对象进行检查。通过设置已知的判断，提前校验该对象是否正确。避免在原子操作期间，因为该对象自身出现的错误而回滚，仅允许系统层面上的错误。从而减少代码复杂度，增强可扩展性和兼容性。
总而言之，原子性的应用分两步走，一是预检，二是应用，通过解耦明确各自职责。

以下是 AI 版本：
原子性是指一个操作或事务被视为不可分割的整体，要么全部成功执行，要么完全回滚到执行前的状态，保证系统的数据一致性。
原子性的核心特性包括：

  1. 不可分割性：操作作为一个整体执行，不能被部分完成
  2. 全有或全无：执行成功时所有效果持久化，失败时所有变更被撤销
  3. 状态一致性：操作前后系统保持逻辑一致的状态
    在实践中，推荐采用”检查-应用”的分离模式：
  • 预检查阶段：在执行原子操作前，验证所有前置条件和业务规则，尽早发现并拒绝无效请求
  • 应用执行阶段：在事务边界内执行实际操作，确保任何失败都能自动回滚
    这种分离模式有助于降低代码复杂度，提高系统的可维护性和可扩展性。但需要注意，预检查不能完全替代事务内的完整性约束，在高并发场景下仍需依赖数据库事务等机制来保证最终的一致性。

换句话说，就是发送一个请求，里面有很多的事务，并在处理该请求期间，务必把全部事务处理完成。如果期间出现错误，则全部回退到设置前的状态。意思是要么成功，要么失败，不能出现中间态，不能“高不成低不就”。这个是提现“每一帧都是完美的”的基础。

Display-Pipeline的生命周期

这里有必要先说明一个 Display-Pipeline 的生命周期：

  • Disable->Enable ：当 DRM 初始化完成后，第一次提交就是指定组件形成一条 Display-Pipeline 并使能。
  • Enable->Page_Flip ：当使能完成后，后续的提交可以是按帧率去更新帧图像，操作对象是 CRTC 和它的 Plane 。
  • Enable->Disable 或 Page_Flip->Disable ：关闭或移除该 Display-Pipeline 。
  • Enable1->Enable2 ：从一个显示模式切换到另一个显示模式。

注意 Disable->Enable ，Enable 请求的 COMMIT SYNC 阶段是仅需与上一个 Disable 请求的 hw_done 同步。

ATOMIC-MODE的阶段

ATOMIC-MODE 分为两部分，第一是 CHECK 阶段，第二是 COMMIT 阶段：

  1. CHECK 阶段：检查提交的请求是否可用。这相当于进行一次模拟，检测请求的 display pipeline 内组件之间的连接和显示模式是否可用。如果不可用，则直接返回相关的错误码。在该阶段不会对硬件做任何操作。
    • Refactor Display-Pipeline 阶段：这是根据指定组件的支持连接的能力，判断组件之间是否可以连接，检查请求的连接是否冲突，冲突了是否处理。如果解决则会被动地牵扯到更多的组件去做重构 Display-Pipeline 的工作。如果不解决则直接返回相关的错误码。
    • Check Display-Mode 阶段：确定新的 Display Pipeline 后，如果当前的新请求配置和目前应用的配置不同，则进行检查。
  2. COMMIT 阶段：这里是对硬件操作的关键节点，但在配置硬件前，需要做同步操作。
    • SYNC 阶段：等待 Framebuffer 被 importer(s) 操作完成。等待上一个的 Atomic 操作的硬件配置完成，用 hw_done 同步；等待上一个的 Atomic 操作的帧扫描完成，发出 Vblank 中断，用 flip_done 同步。
    • Real Commit 阶段：该阶段是真正涉及硬件操作部分，如果是 mode_set ，则是对 Display-Pipeline 完整配置一遍，如果是 Page_Flip ，则是仅对 Display-Pipeline 的 CRTC 和它的 Plane 进行配置，更换帧图像。而且硬件配置完成后，触发 hw_done 同步；等待 CRTC 扫描完一帧，触发 flip_done 同步；最后清除完当前帧缓冲区，触发 cleanup_done 同步。

如果在 Real Commit 阶段前不进行同步操作，则：

  1. 在扫描当前 Commit 请求的一帧的 Framebuffer 的同时，合成器或渲染器还正在对该 Framebuffer 进行合成或渲染。双方的异步操作从而导致这一帧的显示图像异常。
  2. 以下以生命周期来设想：
    1. 对于 Disable->Enable ：当上一个 Commit 请求的硬件参数正在配置时，用户提交新的 Commit 请求，导致硬件的寄存器值，一部分是上一个请求的，一部分是当前请求的，后果是不可预想的。
    2. 对于其它的生命周期：当上一个 Commit 已提交的帧正在被 CRTC 扫描的同时，用户提交并处理新的 Commit 请求，导致屏幕显示的一帧的上部分是上一个 Commit 的，下部分是当前的 Commit 的，导致画面撕裂。

总得来说，这里的同步涉及两方面：

  1. Importer 和 Exporter 的关系：一帧的 Framebuffer 被渲染和合成完成后才能被扫描，统称为 In-Fence 。
  2. 上一帧的 Commit 和当前的 Commit ：当硬件配置完成，且一帧图像被 CRTC 扫描完成后，当前 Commit 才能被处理，统称为 Out-Fence ,这个依赖于 VBlank 机制。
ATOMIC请求的结构

新的问题来了，如何描述一个 ATOMIC 请求？
结合上文讲的概念，我们需要一个事务型，或者说是状态型的结构体来描述这个 ATOMIC 请求。这样在 CHECK 阶段出错时，就能把这个状态扔掉，不会应用到硬件，硬件仍使用之前应用的配置，继续正常运作。
那它具体的样子是什么？换句话说，用户可以操控 Display Pipeline 中的哪个组件节点？以下是一个常规的 Display Pipeline ：

  • 对于 Plane(s) ，用户需要给它指定 Framebuffer 地址、分辨率和像素格式等基础属性，才能让 CRTC 从它读取像素数据，并输出到目标屏幕。
  • 对于 CRTC ，它最基本的功能是时序发生器，用户在 Connector 获取的 EDID 或时序去设置。
  • 对于 Connector ，它代表一个目标屏幕，用户需要指定目标屏幕去显示。

那么 Encoder 呢 ？
Encoder 的作用是把从 CRTC 输出的像素数据流，转换为目标屏幕所需的像素数据流。必要时，要对时序时钟做转换输出，还要调整电气属性等等。
在整条像素流当中，CRTC 是起点， Connector 是终点。Connector 的类型，以及用户指定的时序等也决定了它能连接哪个 Encoder 。另外，在整个系统中，在已知有多少个 CRTC 的基础下（多少条像素流），Encoder 代表了这个系统支持哪些类型的 Connector 。一个 Encoder 只能连接一个 Connector 。当用户指定一个 Connector 显示时， DRM 驱动会找一个适合的 Encoder 并与之绑定。所以用户可以不用关心 Encoder ，因为它们本就是“一体”的。
从实际的情况去理解，比如说嵌入式领域和桌面 PC 。

  • 在嵌入式领域，在设备树中记录了显示模组的各个组件，一个节点对应一个组件，用 port:endpoint 子节点预先连接各个组件，来表示各组件之间的关系。比如说： LDB 即是 Encoder ，也是 Connector 。所以在嵌入式中，Connector 和 Encoder 之间的关系很简单。
  • 在桌面 PC 领域，它是用 ACPI 表或 PCI 来枚举显示模组。常见机箱引出的显示接口，一般有 DP 、HDMI 和 VGA 等。这些接口是各 Encoder 的输出端，所以说也很简单，一个 Encoder 对应一个 Connector 。

所以，用户不需要额外指定 Encoder ，指定 Connector 就间接指定了 Encoder 。

当用户指定组件并发送 ATOMIC 请求后，进入 CHECK 阶段，根据指定的组件，重构 Display-Pipeline ；在新的 Display-Pipeline ，从 Connector 开始，到 CRTC/Plane 结束，检查显示参数是否可行。
然后到 COMMIT 阶段，这是运用阶段。这里产生一个问题，当请求内的参数已经应用在对应的组件硬件后，这些参数还需要保留吗？保留在哪里？
其实很简单，请求成功应用之后，可以把这个请求作为状态挂在对应的组件描述符上，表示当前组件正在应用这个请求的属性。而且下次有新的请求时，比如说更换时序参数、关闭 Display-Pipeline 等等，可以先继承当前状态的属性，再去合并新属性，不需要从零开始填充该新请求。而且在 Refactor Display-Pipeline 阶段，给根据当前状态和新请求去更新出中间状态（当前状态和新请求的状态之间的不同状态），这个会影响在 Real Commit 阶段的执行（这个将在后续详细说明）。
举个简单的例子，比如说当前的 Display-Pipeline 是处于关闭状态，这时来了一个新请求，就是把它开启（出现中间状态：使能状态改变）。由于关闭后，该 Display-Pipeline 的各组件的寄存器值是未知的。而且重新使能后，第一步操作是 reset ，硬件特性的不同，其寄存器恢复为默认值。我们可以把各组件描述符当前记录的状态，比如说时序、分辨率和像素格式等，继承到新请求（只要用户在此前关闭时，不把配置移除，在重新使能时用户也不用重新上传一次配置）。在 ATOMIC 操作执行期间，直接应用这些继承的配置去设置各组件的寄存器（根据中间状态在 Real Commit 阶段执行使能操作）。

各组件（除了 drm_encoder ）的 new_state 继承当前组件挂载的配置，即 old_state 。它们的 funcs 都有一个名为 atomic_duplicate_state() 的回调函数，它的作用是把当前正在使用的 state 复制到新的 state ，但是并不是完全复制，会把中间状态清除。中间状态是当前组件正在应用的状态和上一次应用的状态的差异。因为 new_state 和当前组件应用的 state 之间的中间状态，将在本次的 Atomic 请求的 Check 阶段生成。
另外，atomic_duplicate_state() 是必须要实现的，而且在 drivers/gpu/drm/drm_atomic_state_helper.c ，定义了一系列的框架级 helper_funcs 。如果相关驱动没有额外的属性，可以直接使用该源代码文件内实现的函数作为 atomic_duplicate_state() 。

当前的 drm_atomic_state 的各个组件配置应用成功后，把 new_state 作为组件的有效状态，挂载到组件的描述符字段 ->state ；把各组件的 old_state 清除，期间调用各组件的 atomic_destory_state() 回调函数。

atomic_destory_state 函数是必须实现的，但在 drm_atomic_state_helper.c 内也有相应的函数实现，可以直接使用。

根据上述说明，总结各组件（除了 drm_encoder ）drm_xxx_state 的迁移流程：

  1. 复制旧状态：通过 atomic_duplicate_state() 复制当前状态到 new_state
  2. 修改新状态：用户/驱动更新 new_state 的配置（如分辨率、FB 地址）
  3. 提交生效：硬件配置应用成功后，new_state 成为当前状态
  4. 清理旧状态：old_state 被释放（调用 atomic_destory_state() ）
主动更新和被动更新

上文说过，drm_atomic_state 是一个事务型结构体，是指当用户发出 Atomic 操作请求时，都会新分配并初始化一个 drm_atomic_state ，内部记录了用户指定更新的组件（主动更新）和因冲突而被迫更新的组件（被动更新）。这是在经过 Check 的 Refactor Display-Pipeline 阶段后，记录的待更新组件。当 Atomic 操作完成后，会把各组件的 old_state 清除，最后把 drm_atomic_state 清除。
其中“主动更新”和“被动更新”，见以下示图：

主动更新和被动更新的操作分别是失能组件和使能组件：

  • 失能操作的流程是“使能->失能”；
  • 使能操作的流程是“失能->使能”，或“使能A->使能B”。

其中“使能A->使能B”是指组件从当前的状态更新到一个新的状态。

其中，被动更新更多表示的是：因组件 A 主动更新导致与组件 B 冲突，组件 B 被迫更新。
用户指定的组件所依赖的组件正在被其他组件使用，如用户指定的 drm_connector0 （对应：drm_connector0更新->主动更新->使能->(失能->使能)）指定的 drm_encoder 正在被 drm_connector1 使用，此时出现两种情况：

  1. 如果用户同时指定了这两个 drm_connectors 去使能
  2. 如果用户仅指定了 drm_connector0 去使能，但没有指定 drm_connector1 去使能，或是指定它去关闭

对于第一种，则出现冲突，因为 drm_encoder 只能被一个 drm_connector 使用，但用户指定了两个，而且还是指向同一个 drm_encoder 。则报错，返回相应的错误码。
对于第二种，如果 drm_connector1 没有被用户指定使能，则它必须让出 drm_encoder 给 drm_connector0 。因此 drm_connector1 也因为此而受到牵连，也加入到当前的 drm_atomic_state ，相关的更新操作是“失能”（对应：drm_connector1更新->被动更新->失能->(使能->失能)）。另外，给 drm_connector1 输出的 drm_crtc0 也会受到牵连：

  1. 如果仅是给 drm_connector1 输出，也会被加入到当前的 drm_atomic_state ，更新操作也是“失能”，因为它没有目标屏幕去输出像素信号了（对应：drm_crtc0更新->被动更新->失能->(使能->失能)）。
  2. 如果还额外给其它 drm_connector 输出，也会被加入到当前的 drm_atomic_state ，更新操作是输出的目标屏幕 drm_connector 结构改变（对应：drm_crtc0更新->被动更新->使能->(使能A->使能B)）。

如果用户指定 drm_connector1 关闭，则相当于主动把 drm_encoder 给 drm_connector0 使用。它相关的更新操作是“失能”（对应：drm_connector1更新->主动更新->失能->(使能->失能)）。

通过以上的说明可知，drm_atomic_state 负责的是增量更新。

ATOMIC操作的BLOCK和NONBLOCK

ATOMIC 操作分为 BLOCK 和 NONBLOCK ，以下是 BLOCK 的流程图：

  1. 用户调用 drm_mode_atomic_ioctl() 发送 Atomic 操作请求。
  2. 新建一个 drm_atomic_state ，并根据用户指定更新的组件，为各个组件新建请求 new_state 。
  3. 调用 drm_atomic_check_only() 进入 CHECK 阶段：
    • 在 CHECK 的 Refactor Display-Pipeline 阶段，检查 drm_atomic_state 记录的组件（用户指定的，属于主动更新）是否可用，检查出因冲突而被迫更新的组件（被动更新，包含使能和失能操作）。换句话说，就是把要关闭的和要开启的组件收集起来，重构当前 drm_device 的 display pipeline(s) 。
    • 在 CHECK 的 Check Display-Mode 阶段，检查 display pipeline 的显示参数是否可用。注意，仅对使能和将要使能的组件检查。组件的检查顺序是沿着 display pipeline 进行，而且是从 drm_connector 开始，反向沿着当前 display pipeline ，一直到 crtc/plane 。因为显示参数是从 drm_connector 获取，应先由它检查；后面到 drm_bridge（如果有） 、drm_encoder ，检查输入和输出的像素格式是否可用；最后到 crtc 和 plane ，检查时序和像素格式是否可用。
  4. 调用 drm_atomic_helper_commit() 进入 COMMIT 阶段：
    • 在 Commit 的 SYNC 阶段，等待当前请求的帧被 importer 操作完成；等待上一个 Commit 的硬件配置完成和帧扫描完成。
    • 到 Real Commit 阶段，只允许硬件致命错误和系统级的报错（如 OOM ）。此阶段会把 new_state 应用到相应组件中，会把 new_state 作为当前应用的副本（作为下次 ATOMIC 操作的继承），把 old_state 移除。以下是详细步骤：
      1. 把 drm_atomic_state 收集的组件的硬件状态关闭，这里也包含将要使能的组件。如果给一条 display pipeline 的节点保持开启状态时，为该 pipeline 更新显示参数，可能会导致显示不正常，而导致后续发生不可预知的事。因为硬件的特性是各种各样的，而且整条 display pipeline 更新显示参数是一件很耗时，且很重要的事（因为“每一帧都是完美的”），所以一个保险的做法是更新参数前，先关闭，完成应用后在重新使能。
      2. 为已使能或将要使能的组件应用配置，然后使能。
      3. Atomic_Begin() 和 Atomic_Flush() 是针对帧更新。这里围绕着当前请求中一帧的更新和更新完成后的同步，其中包含开启 VBlank 机制（包括中断）、更新Plane 的 Framebuffer 地址、分辨率、像素格式和使能 shadow 等等。
      4. 发出 hw_done 同步，并等待 flip_done ，即等待当前请求的帧扫描完成。
  5. CRTC 发出 VBlank 中断，说明当前请求的帧扫描已完成，会在对应中断处理程序发出 flip_done 同步。
  6. 这个步骤是可选的，如果硬件需要当前帧的 Framebuffer 被扫描完成后立即释放，则这里执行该机制地方。当执行完成后发出 cleanup_done 同步。
  7. 把组件的 old_state 清除，new_state 记录到组件的 ->state 作副本。当前 drm_atomic_state 清除。当前的 ATOMIC 请求已完成，返回到用户空间。

接下来是 NONBLOCK 流程图，不同颜色代表不同的执行流：

与 BLOCK 不同的是，该机制是不等待上一个 ATOMIC 请求完成，如果没完成，则直接返回 -EBUSY 错误码。另外，当 CHECK 阶段成功后，把 SYNC 和 Real Commit 阶段放到 WorkQueue 执行。注意该 WorkQueue 是可被阻塞的。
该机制是把由一条执行流完成的 ATOMIC 请求拆分为两条。把 COMMIT 阶段加入到 WorkQueue 后，

  1. 返回到用户进程执行自己的事务，比如做一系列的同步操作；通知 compositor 可以合成下一帧的图像等等。
  2. 此时的另一边，工作线程正在执行当前 ATOMIC 请求的 COMMIT 阶段，包括等待 In-Fence 被触发，然后把配置应用到硬件。

当双方都完成自己的任务后，等待 LCD Controller 发出的 VBlank ，即一帧的扫描完成。
当接收到 VBlank 中断后，表示可以 flip_done 同步，

  1. 应用进程从 poll_wait 的等待队列唤醒，从 poll() 返回
  2. 执行 COMMIT 阶段的工作线程被唤醒，把当前帧对应 Framebuffer 清除（如果有需求），发出 cleanup_done 同步。最后把组件的 old_state 清除，把前 drm_atomic_state 释放。

mode_set

先记住一个要点：mode_set 的本质是一发而动全身。
该机制对应的核心函数是 drm_atomic_helper_set_config() ，这个函数是框架级 helper 函数，可以理解为它是一个如何使用 mode_set 的标准函数。这个机制是基于 ATMOIC-MODE 机制，调用期间先获取一个新的 drm_atomic_state ，再根据 drm_mode_set 的设置分配并设置各组件的 drm_xxx_state ，给它们作一系列的检查，最后提交请求，操作硬件使其配置生效。
函数 drm_atomic_helper_set_config() 可以作为 drm_crtc->funcs 的 set_config() 的回调函数，也可以会被其它机制内部封装。对于它作为 set_config() 的回调函数， set_config() 会被 drm_mode_setcrtc() 或 __drm_mode_set_config_internal() 调用。而且 drm_mode_setcrtc() 是 drm ioctl 的一份子，意思就是说用户进程可调用此函数去设置 mode_set 。

但 drm_mode_setcrtc() 已经逐步不被使用，转而去使用 drm_mode_atomic_ioctl() ，比如说 wayland-weston 。因为 Wayland 是一个协议，注重于通用性，基于 drm_mode_object 和 drm_property 去操作组件。而 drm_mode_atomic_ioctl() 就是操作它们的统一接口（发送 atomic commit 的统一接口）。
但是不管怎么样，先通过 drm_atomic_helper_set_config() 了解一下 ATOMIC 的 mode_set 也是有必要的。因为相关参数所用到的结构体 struct drm_mode_set 表示需要什么参数去指定并操作一个 display pipeline 。

为什么先指定获取 drm_plane ，再指定 drm_connector ，再到 drm_encoder 和 drm_crtc ？
尤其是 primary plane ，一个 drm_plane ，它表示它能被哪种像素格式被填充，显存有多大，还有高级特性如叠加 plane 和透明 plane 等特性。这些特性都是在 GEM 创建显存的关键。而 drm_connector 是目标对象，也是对于开发者来说在调试整条 display pipeline 中最容易察觉的 debug 对象。drm_connector 存储着它的显示参数，其中最基本的如像素格式、分辨率和时序参数等等（但是 DRM 并没有实现与像素格式相关的属性，这个视 DRM 驱动而定）。 用户进程需要时序参数和分辨率等检查 drm_encoder 和 drm_crtc 才能被使用。
那么为什么要先从 drm_encoder 开始？因为 drm_connector 和它是一体的，这个是根据类型决定的。

为什么步骤中出现很多的 IOCTL 0xB9 和 0xAA ？
0xB9 对应的 API 函数是 drm_mode_obj_get_properties_ioctl() ，对应的参数结构体是 struct drm_mode_obj_get_properties 。调用该函数必须要指定组件，获取组件的所有 drm_property 的 ID 号和当前值。
0xAA 对应的 API 函数是 drm_mode_getproperty_ioctl() ，对应的参数结构体是 struct drm_mode_get_property 。调用该函数必须要指定 drm_property 的 ID 号，获取该属性的类似、值、名字和 flags 等。
结合以上的说明可知，用户进程想要获取组件的所有属性，则需要先获取所有属性的 ID 号形成一个数组，再指定属性去获取更多详细的信息去填充。这样在用户进程也能像 DRM 的组件那样有 struct drm_object_properties 。

为什么 drm_encoder 没有 drm_property ？
通过以上的疑问和解答可知，组件的 base 对象 drm_mode_object 和它的 drm_property ，都是开放给用户进程搭建出简易显示框架。而 drm_encoder 除了有 drm_mode_object 作为 base 对象外，为什么没有 drm_property ？这是因为它本身就很“简单”，但是又“不简单”。“简单”在于它只是把从 drm_crtc 输出的像素信号转换为它自己的像素信号再输出。“不简单”在于它还有对象为 drm_bridge 的 bridge_chain 。就目前的硬件结构来说， Encoder 仅对应一个 Connector 。对于用户进程来说，指定一个 Connector ，相当于也指定了 Encoder 。用户指定的目标屏幕 Connector 本身带有像素信号转换的信息要素在，这些都应由系统搞定。

在第八个步骤中，为什么是从 drm_crtc 读出 drm_framebuffer 信息？
从大多数讲，该步骤读出的 drm_framebuffer 是 drm_crtc 的 primary plane 。从硬件的角度出发， CRTC 是从显存获取像素数据，再输出到 Encoder ，最后到显示屏。从 DRM 角度出发， drm_framebuffer 是当前 drm_crtc 的 plane 的实例对象，而且 drm_framebuffer 是 GEM 和 KMS 之间的桥梁。从用户进程出发，显存是需要使用时才会被分配使用，换句话说，就是仅用户进程需要显示时才会需要用到显存，这里分别充当着生产者和消费者。用户进程记录着它自己获取的 drm_framebuffer 的 ID ，可以用它与从 IOCTL 0xA1 获取的 drm_framebuffer 匹配。
但是如果本次流程是初始化 DRM 后的第一次 ATOMIC 操作请求，则 drm_crtc 没有记录 primary plane 的 framebuffer ID ，为 NULL 。

该机制是 Out-Fence 的核心部件。DRM 引出了两个方法给应用层使用 Out-Fence 进行同步。

总得来说，这机制是用于用户发送 NONBLOCK 的 Atomic 操作请求。当当前请求的 Commit 阶段加入到工作队列后，就会返回到用户空间。用户进程可以使用以上两个的任意一个机制去同步等待。
这两个方法的最终目的是一致的，但为什么要用不同的方式进行同步？
这是不同的场景下使用的。如果仅仅是单纯的显示画面，则只用第二个方法即可。而第一种方法是用在多设备之间共享 Framebuffer 的场景，比如说 VPU 把解码出来的视频画面合成到显存中，再把它输送给 DPU 输出。这里就涉及到两个设备之间对同一显存的同步，所以使用第一个方法更为适宜。
从使用角度上理解，从 dma-fence 转换而来的 FD ，它面向的对象是这两个设备，属于跨设备级别的 FD 。而第二个方法 /dev/dri/cardX 的 FD 则仅面向 DRM ，或者说是显示功能，这个单一的对象。

这里先说明 CRTC 的状态。
在 CRTC 中存在很多的状态位，它的 drm_crtc_state 包含上文讲过的 enable 和 active 状态，还有 mode_changed 、active_changed 、connectors_changed 和 planes_changed 等等。下面将说明它们之前的联系和由来，了解它们的作用后，就能理解 ATOMIC COMMIT 的执行流程。

mode_changed 的作用是什么？
当检测到当前 drm_crtc 的 old_state 存储的显示参数和 new_state 的不同时，new_state 的 mode_changed 被标记为 True 。
active_changed 的作用是什么？
当检测到当前 drm_crtc 的 old_state 的 active 状态位和 new_state 的不同时，new_state 的 active_changed 被标记为 True 。
connector_changed 和 planes_changed 的作用是什么？
当检测到当前 drm_crtc 的 old_state 连接的 drm_connecotor(s) 以及 drm_plane(s) ，和 new_state 的不同时，new_state 的 connectors_changed 和 planes_changed 被标记为 True 。

为什么需要 mode_changed ？ 它和 enable 之前的联系是什么？
上文讲过 enable 的作用为当前 drm_crtc 的 new_state 标记显示参数是否可用。它仅注重于表示 drm_crtc 的 drm_crtc_state 状态（不管是 old_state 还是 new_state ），继而延伸到整条 display pipeline（用 drm_xxx_state 描述的 pipeline ）。而 mode_changed 注重于 old_state 到 new_state 之间的状态，即中间状态。需要利用它来标注对应的 drm_crtc 需要更新。
显示模式的改变分为三类：

  1. 从无到有，即原先 old_state 没有显示参数，到现在 new_state 有显示参数
  2. 从有到无，即原先 old_state 有显示参数，到现在 new_state 没有显示参数
  3. 从原先模式更换为另一个模式，即原先 old_state 有显示参数 1 ，到现在 new_state 有显示参数 2

尤其是第三类，仅靠 enable 并不足以表示 old_state 和 new_state 之间的改变，因为它们的 enable 都为 True 。这时就需要 mode_changed 来表示有新的显示参数需要处理，这就是 mode_changed 的由来。

为什么需要 active_changed ？
与它相关的状态位是 active ，上文讲过，它的作用是当前 drm_crtc 是否开启。与 enable 同理，它也仅注重于表示 drm_crtc 的 drm_crtc_state 状态，继而延伸到整条 display pipeline 。而 active_changed 注重于 old_state 到 new_state 之间的状态，即中间状态。它依赖于 active ，而 active 依赖于 enable 。仅有在 enable 为 True 时，active 才有效。而 active_changed 唯一作用就是：在 drm_crtc 的 old_state 和 new_state 的 enable 都为 True 时（不管它们之间的显示参数是否一致），如果是从“开启->关闭”或“关闭->开启”的操作，仅有 active_changed 去记录之间的转变。

DRM 所需的，又或者是用户进程所需的分辨率和像素格式等，都是从 drm_connector ，即显示屏获取。对于带有 EDID 的显示屏，则可以获取并解析 EDID ，把解析出来的信息下发到用户空间，找到合适的像素格式，根据此并结合 drm_crtc 支持的输入端像素格式去获取显存。然后 drm_plane 所属的 drm_crtc 也会根据此去输出正确的像素格式到目标屏幕。但是对于没有 EDID 的显示屏，情况就稍微复杂了点。由于没有 EDID ，用户空间就无法获取到它，而且 DRM 框架中并没有类似于 “bus format” 的 drm_property（除非驱动去实现类似的属性，并在 libdrm 中对该属性的支持）。则不管是第一次 ATOMIC 请求前后，还是后续的 ATOMIC 请求，用户进程仅知道 drm_crtc 支持的输入端像素格式，但不知道它的输出端像素格式，更不知道目标屏幕所需的像素格式了。那么只能从 “drm_crtc 支持的输入端像素格式” 列表中，选择第一个像素格式去获取显存。比如说最典型的，就是把 RGB888 放到此列表中的第一位，因为它是大多数屏幕默认支持的像素格式。但是这对于其它屏幕来说，这不是一次好事。

结合代码简单说明 SYNC 阶段：

  1. 等待上一个 ATOMIC 操作完成，准确来说是等待它的 flip_done 完成。但是如果当前 COMMIT 是 Nonblock ，则不能等待，返回 -EBUSY 。 Nonblock Commit 适用于 Page_Flip ，非 Nonblock Commit 适用于 mode_set 。
  2. 新建一个 COMMIT 描述符
  3. 把 ATOMIC 请求的各组件 new_state 作为当前的 state ，把 old_state 则被清除。意思是当前请求的配置可以被应用，当前正在应用的配置可以移除，用新的配置了。
  4. 等待 plane(s) 的 In-Fence 被 signalled 。换句话说就是等待 Plane 对应的 Framebuffer 被 importer 处理完成。其中 importer 指的是 Render 或 Compositor 。

Real Commit 阶段：

  1. 根据 ATOMIC 请求的组件，尤其是更换显示模式的组件，把它们关闭。避免因硬件配置的更新，导致出现短暂的画面异常。
  2. 根据 ATOMIC 请求的组件，以及 CRTC 的 enable==true 、 active==true 和相关的 changed 状态去使能 Display Pipeline ，更新相关组件配置，如时序、分辨率等等。
  3. 帧更新，特指 CRTC 和 Plane ，更改 Plane 的硬件属性，如 Framebuffer 地址、像素格式、 pitch 和使能 shadow 机制。
  4. 以上硬件操作完成后，发出 hw_done ，等待 flip_done ，即等待当前 COMMIT 对应的帧被扫描完成。
  5. 等待 filp_done 完成后，清除当前帧的 Framebuffer （可选，视硬件特性而定），发出 cleanup_done 同步。

对于 Page_Flip ，忽略第一和第二阶段。

现在来看 drm_crtc_commit 的定义：

  • crtc ：表示这个 drm_crtc_commit 是给哪个 CRTC 使用的
  • ref ：引用计数，初始化为 1 ，为 0 时释放 drm_crtc_commit 。每有一个组件引用它时，对应的引用计数加 1 ，取消引用就减 1 。这个引用计数是 drm_crtc_commit 的生命周期（或者说引用计数本身的作用就是这个），当一个 Atomic 请求的完成，表示一个 drm_crtc_commit 的完成。
  • filp_done ：当完成一帧的扫描后，给该 completion 触发同步。与此同时，Out-Fence 也触发同步，如果应用进程也通过 poll() 等待该同步，则会被唤醒。
  • hw_done ：当硬件应用配置完成后，给该 completion 触发同步。尤其是生命周期 Disable->Enable ，因为能让执行 Enable 请求的执行流清楚地知道 Disable 请求已被硬件应用的信号是 hw_done ，而不是 flip_done 。
  • cleanup_done ：当当前 ATOMIC 请求的帧请求完成后，如果有需求，可以把帧对应的 Framebuffer 请求，然后给该 completion 触发同步。
  • commit_entry ：把即将执行 Real Commit 的 drm_crtc_commit 链接起来（头插法），处理完成后移除。该链表的头部是 crtc->commit_list 。当当前 ATOMIC 请求要确认上一个请求是否已完成时，如果该链表为空，则表示已完成，如果该链表的第一个是上一个请求的 drm_crtc_commit （有且仅有一个），则表示它的 flip_done 还未同步。
  • event ：记录 VBlank 的同步事件描述符。该事件用于触发 flip_done 同步，触发 Out-Fence 同步，这是每个 ATOMIC 请求必有的同步事件。该字段仅用于用户进程不使用 VBlank 同步事件进行同步时，新建一个 VBlank 给当前 Atomic 操作使用，并临时记录到 event 字段。如果在进行 COMMIT 的 Real Commit 阶段前出现报错，则可以在后续的释放空间时，根据该字段把该同步事件清除。如果成功进入，则把该字段设为 NULL 。
  • abort_completion ：这个默认为 True ，这个是在新建 drm_crtc_commit 后，在进行 Real Commit 之前时使用，是否清除该 drm_crtc_commit 。

  • 对于生命周期 Enable->Disable ：即上一个 Atomic 请求的 CRTC 的 Active 为 True ，当前 Atomic 请求的为 False ，即这两个请求之间的 active_changed 为 Ture 。对于当前 Atomic 请求的 Connector ，它没有指定 best_encoder ，但对应的硬件状态中，它还在使用在上一个 Atomic 操作请求指定的 best_encoder 。在该函数中，根据当前它正在应用的配置（old_state）找到 best_encoder ，把该 Encoder 关闭。然后把当前 Atomic 请求的 CRTC 关闭。
  • 对于生命周期 Enable1->Enable2 ：即上一个 Atomic 请求的 CRTC 的显示模式，与当前 Atomic 请求的不一样，即这两个请求之间的 mode_changed 和 connector_changed 都为 Ture（改变显示模式的一部分原因是目标屏幕的改变）。对于当前 Atomic 请求的 CRTC 指定输出的 Connector ，它在上一个 Atomic 操作请求指定的 best_encoder 必须关闭。它在当前请求中指定新的 best_encoder ，这个 Encoder 可能在上一个 Atomic 请求中已指定给它使用，则经由它来关闭；可能它在上一个请求中被指定给其它 Connector 使用，则经由该 Connector 来关闭；也可能它根本没有被其它 Connector 使用，则不需要关闭。然后把当前 Atomic 请求的 CRTC 关闭。
  • 对于生命周期 Disable->Enable ：即上一个 Atomic 请求的 CRTC 的 Active 为 False ，当前 Atomic 请求的为 True ，即这两个请求之间的 active_changed 为 Ture 。对于当前 Atomic 操作请求的 CRTC 指定输出的 Connector ，它在上一个 Atomic 操作请求是关闭操作，即没有指定任何组件，包括 CRTC 和 Encoder 。在当前操作请求中它有指定 best_encoder ，这个 Encoder 可能在上一个 Atomic 请求中已被指定给其它 Connector 使用，则经由该 Connector 来关闭；也可能它根本没有被其它 Connector 使用，则不需要关闭。另外当前 Atomic 请求的 CRTC 需要关闭。
  • 对于 Page_Flip ：请求为 Page_Flip 的 Atomic 请求无任何中间状态（*_changed），而且 CRTC 的 Active 为 True ，、跳过该函数。

为什么从 Connector 开始关闭 Display-Pipeline ？
因为 Connector 是 Display-Pipeline 的终点。硬件接收到 CPU 写入寄存器的配置后做相关操作是需要时间的，而且硬件的运行和 CPU 的执行是异步的。如果关闭操作和后续的使能操作一致“先从 CRTC 开始，最后到 Connector”，则可能会出现一个情况。就是 Encoder 对应的硬件将进行或正在进行关闭操作时，CPU 操控 CRTC 对应的硬件寄存器，使其进行使能操作（CPU 执行指令是很快的，不用质疑），这时 Encoder 可能还保持之前的配置来接收并输出像素数据，使得与之连接的目标屏幕出现一些异常画面。这个情况尤其是针对 生命周期 Enable1->Enable2 。

    1. 生成新的 drm_atomic_states ，根据主动更新的需求，继承当前 state 并生成对应的 new_state 。而且对于 Page_Flip ，仅涉及到 Plane 和 CRTC 。注意在此期间会涉及到数据共享，需要用到 drm_modeset_lock 来确保一致性。

vblank

VBlank 是什么？
每当 LCD Controller 扫描完一帧图像后，进入 VFP (Vertical Front Porch) 。见以下视图：

在此阶段，可以在 VSync 之前，准备好下一帧图像。那么这需要 LCD Controller 在进入 VFP 同时，发出中断到 CPU ，通知一帧扫描的结束，让进程准备好下一帧图像。而这个中断，被称为 VBlank 中断。

那么 VBlank 中断在 DRM 中的作用是什么？
每一次的 ATOMIC 操作，不管是 mode_set 还是 Page_Flip ，都要当 LCD Controller 完成扫描该 Atomic 操作对应的帧，发出 VBlank 中断后，才能表示当前 ATOMIC 操作进入收尾阶段。这是因为“每一帧都是完美的”，要保证当前 Atomic 操作的硬件设置，要完整地在当前帧“呈现”出来。
在 ATOMIC 操作中，有三个同步机制，这里简单回顾一下：

  • hw_done ：表示 Display Pipeline 上的组件的硬件设置已完成
  • flip_done ：表示该 Atomic 操作对应的帧已被 LCD Controller 扫描完成
  • clean_done ：表示当前帧对应的显存已被清除（由硬件特性决定）

下文将要说明的开启/关闭 VBlank ，并不是仅仅是指向 VBlank 中断，而是整个机制。而且 VBlank 中断是这个机制的一部分，关联性强。下面讲解的 VBlank ，是指整个机制，而 VBlank 中断，则仅仅是中断。

在发出 VBlank 中断后，表示同步机制 flip_done 已触发，表示可以进行下一个 ATOMIC 操作。

那么 VBlank 又是如何与 ATOMIC 操作联系在一起？
VBlank 是 CRTC 的一部分， CRTC 是 ATOMIC 操作的操作对象，那么 VBlank 也是 ATOMIC 操作的操作对象。
以 CRTC 驱动支持使能/关闭/处理 VBlank 中断为基础，再引出两个基础：

  1. 需要用到时，才会把 VBlank 使能。这里的“用到”，指的是接收到当前或未来一帧完成后的 VBlank 中断时，必须有相关的同步事件需要处理。
  2. 强制关闭 VBlank 后，此前与该 VBlank 绑定的同步事件都将无效，在解除“强制关闭”前绑定的事件也处理不了。

简而言之，第一个基础是 “按需开启” ，第二个基础是 “强制关闭” 。

这里举个例子来说明。就比如一个游乐场早上 8 点到晚上 8 点营业。但游乐场为了省电费，有游客后才会把所有游乐设施开启，没有游客就会把所有设施关闭。
每一名游客进入游乐场前都需要取票，从游乐场离开后，需要放票 。
到晚上 8 点整，强制所有游客离开游乐场，强制他们放票，并把所有游乐设施关闭。次日早上 8 点后，游乐场开启，游客可取票继续游玩。

基于第一个基础，对应的实现是，使用引用计数 refcount ，来记录当前 VBlank 的同步事件绑定情况。当 refcount > 0 时，表示有同步事件需要在 VBlank 中断期间同步。当处理完一件同步事件后，把 refcount 减一。

根据以上基础，引出两个系列的函数： drm_crtc_vblank_on/off() 和 drm_crtc_vblank_get/put() 。

  • drm_crtc_vblank_get() ：使得 refcount+1 ，且得知 refcount==1 时，使能 VBlank ，但是如果此前已强制关闭，则无法开启。
  • drm_crtc_vblank_put() ：使得 refcount-1 ，且得知 refcount==0 时，关闭 VBlank 。
  • drm_crtc_vblank_off() ：强制关闭 VBlank ，此前与该 VBlank 绑定的同步事件都将在此时提前处理，而且在调用 drm_crtc_vblank_on() 前绑定的事件是不被处理的，因为 VBlank 中断已被关闭。
  • drm_crtc_vblank_on() ：该函数与 drm_crtc_vblank_off() 对应，解除“关闭”。而且如果 refcount > 0 ，使能 VBlank 。

结合以上游乐场的例子：

  • drm_crtc_vblank_get() 对应取票；
  • drm_crtc_vblank_put() 对应放票；
  • drm_crtc_vblank_off() 对应强制关闭游乐场，并让所有游客放票；
  • drm_crtc_vblank_on() 对应再次开启游乐场。

仅单拎出一个函数来说明它的作用是不够的，以上函数需要根据以上两个基础，和其它函数来配合使用。
这些函数之间有一个共性，就是都支持使能/失能 VBlank 。这些使能/失能操作是基于 ATOMIC 操作的流程来的。
比如根据 mode_set 的 ATOMIC 操作对硬件操作的执行流程， VBlank 的使能/失能操作如下：

  1. modeset_disables
    • REAL COMMIT ：调用 drm_atomic_helper_commit_modeset_disables() ，关闭 Display Pipeline 。
    • 在内的 VBlank ：调用 drm_crtc_vblank_off() 来强制关闭 VBlank ，并把之前绑定的同步事件在此阶段处理。
  2. modeset_enables
    • REAL COMMIT ：调用 drm_atomic_helper_commit_modeset_enables() ，使能 Display Pipeline ，期间会涉及到时序、分辨率和时钟等硬件设置。
    • 在内的 VBlank ：调用 drm_crtc_vblank_on() ，如果检测到 refcount > 0 时，使能 VBlank ，包含 VBlank 中断，遵循第一个基础。
  3. planes （帧更新）
    • REAL COMMIT ：调用 drm_atomic_helper_commit_planes() ，更改 Plane 的硬件属性，如 Framebuffer 地址、像素格式、 pitch 和使能 shadow 机制等。
    • 在内的 VBlank ：调用 drm_crtc_arm_vblank_event() 把 flip_done 作为同步事件绑定到指定的 VBlank ，期间调用了 drm_crtc_vblank_get() 。
  4. wait_for_vblanks
    • REAL COMMIT ：调用 drm_atomic_helper_wait_for_vblanks() ，等待当前 COMMIT 对应的一帧完成。期间调用 drm_crtc_vblank_get() ，所以说这个也是针对该 VBlank 的同步事件。
  5. VBlank 中断发出后
    • VBlank Handler ：调用 drm_crtc_handle_vblank() ，处理与该 VBlank 绑定的同步事件。每处理完成一件同步事件，调用一次 drm_crtc_vblank_put() 。而且当 refcount==0 时，关闭 VBlank 。
    • REAL COMMIT ：从 drm_atomic_helper_wait_for_vblanks() 返回，且在此之前调用了 drm_crtc_vblank_put() 。

注意：
第 2 个步骤和第 3 个步骤会因硬件特性而顺序对调。
对于 Page_Flip ，则从第 3 个步骤开始。

从 REAL COMMIT 流程可知， drm_crtc_vblank_off() 和 drm_crtc_vblank_on() 是绑定在一起的，而且是调用 drm_crtc_vblank_off() 后，才能调用 drm_crtc_vblank_on() 。否则只调用 drm_crtc_vblank_on() 是没有作用的。后续将详细说明这些函数，以及它们之间的关系。

由于该结构体在 drm_vblank.h 声明，有很详细的注释说明，以下是作者目前对这些字段的理解：

  • queue ：这个多数是给 ATOMIC 操作使用的。根据上文所知，每当 VBlank 中断发出后，当前的 ATOMIC 操作才能进入收尾阶段。其中最有代表性的函数为 drm_atomic_helper_wait_for_vblanks() 。当当前的 ATOMIC 操作完成硬件操作后，需要调用该函数，来等待该操作对应的帧扫描完成后， LCD Controller 发出的 VBlank 中断。该函数就是把执行当前 ATOMIC Real Commit 的线程加入到对应 drm_vblank_crtc 的等待队列 queue 。另外，应用进程也可系统调用 drm_wait_vblank_ioctl() ，加入到该等待队列，等待一帧图像的扫描完成。

  • disable_timer ：这是延迟关闭 VBlank 所用到的定时器，仅在 drm_crtc_vblank_put() 的关闭 VBlank 使用。根据上文可知，当 refcount==0 时，可以把 VBlank 机制关闭，那为什么需要使用定时器来延迟关闭？这个延迟关闭由硬件决定是否开启，可以每扫完一帧后立刻关闭，换下一帧前再开启；也可以扫完一帧且后续都处于 IDLE 后，再关闭。在目前的 DRM 框架中，延迟关闭是默认开启的，除非在 drm_device 中，把 vblank_disable_immediate 设为 True 。延迟关闭的优点是不用每次页面翻转期间频繁开关 VBlank ；缺点是进入 IDLE 阶段时，会有一小段时间（大概在一帧以内）每扫描完一帧后，发出 Vblank 中断，直到定时器时间到。

  • seqlock ：保护字段 count 和 time 时用到。

  • count ：也可以理解它为 seq ，该字段是每当扫描完一帧后， count 被累加。如果 LCD Controller 没有硬件计数器，则每次扫完一帧后，count+1 ；如果有，则根据硬件计数器累加，但一般是 count+1 。这个字段的作用是给同步事件做基准，意思是可根据此字段要求同步事件在未来的第几帧处理，详细见 drm_crtc_arm_vblank_event() 和 drm_crtc_handle_vblank() 的实现。

  • time ：这是一个时间戳，每触发一次 VBlank 中断，就记录此时的时间戳。

  • refcount ：当一个同步事件与当前 VBlank 绑定时，该字段加 1 ，当处理完成事件后，该字段减 1 。另外，由于“按需开启”和“强制关闭”，该字段和字段 inmodeset 之间有配合操作，使其支持这些基础。

  • last ：这个与硬件计数器有关。如果 LCD Controller 不支持硬件计数器，则该字段永远为 0 ；如果支持，则每触发一次 VBlank 中断，读出当前硬件计数器的数值，并记录到该字段。注意，如果 LCD Controller 支持硬件计数器，该字段也与 count 有一定的关系。换句话说，count 的累加与它有关，详细见函数 drm_update_vblank_count() 的实现。

  • max_vblank_count ：这个与硬件计数器有关。如果 LCD Controller 不支持硬件计数器，则该字段永远为 0 ；如果支持，则记录当前硬件计数器所支持的最大值是多少。如果超过这个值，则表示溢出，从 0 开始。

  • inmodeset ：该字段是二个基础实现的关键之一，需要和 refcount 配合使用。调用 drm_crtc_vblank_off() 后，把 inmodeset 置为一，并把 refcount+1 ，表示处于关闭状态。当 drm_crtc 被关闭时，通过此字段和 refcount 检测对应的 VBlank 机制是否还处于开启状态，这个在 drm_atomic_helper_commit_modeset_disables() 体现。调用 drm_crtc_vblank_on() 后，inmodeset 被清除，refcount-1 。

    为什么把 inmodeset 置为一，并把 refcount+1 ，就表示 VBlank 处于关闭状态？因为调用 drm_crtc_vblank_get() 后，检测到 refcount 等于 1 时，会自动把 VBlank 使能。而调用 drm_crtc_vblank_off() 强制关闭时，把 refcount+1 ，使其调用 drm_crtc_vblank_get() 后，永远使 refcount > 1 ，它就触发不了 refcount 等于 1 就使能 VBlank 。

  • pipe ：与 drm_crtc->index 一致。换句话说， drm_crtc 和 drm_vblank_crtc 本就是一体的。

  • framedur_ns ：记录扫描一帧图像需要多少时间，在 ATOMIC 操作的 REAL COMMIT 阶段，可调用 drm_atomic_helper_calc_timestamping_constants() 来计算时间。

  • linedur_ns ：记录扫描一行图像需要多少时间，在 ATOMIC 操作的 REAL COMMIT 阶段，可调用 drm_atomic_helper_calc_timestamping_constants() 来计算时间。

  • enabled ：记录 VBlank 的使能状态。为 True 表示 VBlank 正在使能中，否则为关闭中。

处理vblank

在接收 VBlank 中断后， VBlank 需要处理什么？
同步事件被分为两种载体，一是 event ，另一个是 worker 。
event 是最常见的，它是一种同步机制，等待当前或未来一帧的图像扫描完成后，即发出 VBlank 中断后，再执行相关操作。而上文所讲的 flip_done ，它是基于 event 来实现同步的。每次进行 ATOMIC 操作时，必须使用该机制，使 flip_done 变为 completed 。当然在实践的过程中，或许也会发现应用程序会系统调用 drm_wait_vblank_ioctl() ，来等待一帧图像的扫描完成，进行同步操作，可以选择使用 event 机制进行同步等待。event 被放置在 drm_device 的 vblank_event_list 链表，可以通过 vblank 的字段 pipe 来匹配。
worker 同样也是同步机制，但与 event 不同是， event 是以事件为对象，而 worker 是以内核线程为对象。意思是当等待当前或未来一帧的图像完成后，会唤醒线程去做相关操作。目前该机制用的比较少，多数是 GPU 需要此机制。

drm_crtc_vblank_on/off()

函数 drm_crtc_vblank_off() 的作用是把 VBlank 强制关闭，并把之前绑定的同步事件在此阶段处理。它把 VBlank 的字段 inmodeset 置为一， refcount+1 。
函数 drm_crtc_vblank_on() 必须在调用 drm_crtc_vblank_off() 后调用。它把 VBlank 的字段 inmodeset 清除， refcount-1 。而且如果检测到 refcount>0 ，则调用 drm_vblank_enable() 使能 VBlank 。

为什么强制关闭后，把同步事件在关闭阶段提前处理？
原因很简单，因为关闭之后就没有 VBlank 中断了，自然就没法在 VBlank 中断阶段处理同步事件。就算在 modeset 的硬件参数更新操作亦是如此，关闭后再重新使能。在调用 drm_crtc_vblank_off() 之后，到调用 drm_crtc_vblank_on() 之前的同步事件绑定，是能在本次 ATOMIC 操作的 VBlank 中断阶段处理的。
另外，因为调用 drm_crtc_vblank_get() 后，会把 refcount+1 ，而且如果检测到 refcount==1 ，把 VBlank 使能。调用 drm_crtc_vblank_off() 后，就不能调用此函数去使能 VBlank ，目的是让 refcount 一直保持大于 1 的状态。后续经过正常的 drm_crtc_vblank_get/put() 都不会把 refcount 小于等于 1 ，除非调用 drm_crtc_vblank_on() 。

如何使用

先从 drm_crtc_vblank_off() 讲起，它用在 drm_crtc->helper_funcs 的 atomic_disable() 内。 drm_crtc 的回调函数 atomic_disable() 被调用在 drm_atomic_helper_commit_modeset_disables() 。由此可知，强制关闭 VBlank 操作是和关闭 drm_crtc 操作绑定的。

再到 drm_crtc_vblank_on() ，它用在 drm_crtc->helper_funcs 的 atomic_begin() 内。 drm_crtc 的回调函数 atomic_begin() 被调用在 drm_atomic_helper_commit_planes() 。根据上文可知，该函数是用于刷新帧，即换下一个帧来扫描时被调用。这个是大多数驱动的做法。
其实 drm_crtc_vblank_on() 也能用在 drm_crtc->helper_funcs 的 atomic_enable() 。drm_crtc 的回调函数 atomic_begin() 被调用在 drm_atomic_helper_commit_modeset_enables() 。这个函数和 drm_atomic_helper_commit_modeset_disables() 相对应，被用在 modeset 。

不管怎么说，与 drm_crtc_vblank_off() 相比， drm_crtc_vblank_on() 相对灵活，但它们是被绑定在一起，不然将失去平衡。
drm_crtc_vblank_on() 调用的位置最终还是以 DRM 驱动而定。

它们与drm_crtc_vblank_get/put()的关系

在执行 mode_set 的过程中，尤其是 commit_tail 阶段，即操作硬件阶段，设置显示模式前（如分辨率、时钟和时序等），是需要让当前 CRTC ，以及它所属的 Display Pipeline 关闭，停止扫描 Framebuffer ，把 VBlank 中断关闭（调用 drm_crtc_vblank_off() ）。不然可能会提前触发 VBlank 中断，使得 DRM 误以为当前 ATOMIC 操作已完成，处理提前设置好的 events 。

为什么在关闭阶段把 VBlank 关闭？
假设在 modeset 之前是 IDLE 阶段，可能是 LCD Controller 在扫描 Framebuffer 时，而且 drm_crtc_vblank_put() 设置的定时任务“关闭 VBlank ” 还未到时间，系统正在进行 ATOMIC 操作的硬件设置阶段。如果不把 VBlank 中断关闭，可能会在硬件设置阶段， LCD Controller 触发 VBlank 中断，使得 DRM 误以为当前 ATOMIC 操作已完成，处理之前与之绑定的同步事件。

如果你把同步事件 flip_done 提前放到 vblank_event_list ，也会处理此 event 。但不推荐提前放置该 event 。而是在 drm_atomic_helper_commit_planes() 阶段，即更新帧阶段放置。这样也能避免在上述阶段，不管是 modeset 还是 Page_Flip 的 ATOMIC 操作，都能在对应的帧被扫描完成后进行同步。

就这些机制，自然而然地让 Vblank 和 drm_file 促成了基于 drm_pending_event 的关系。

总结

总得来说，VBlank 的出现就是防止画面撕裂，因为它的出现是确保一帧对应的 Framebuffer 还未扫描完成前，都不能被影响，被篡改。同时它也是 ATOMIC 操作的核心之一（out-fence），保证每一帧都是完美的。
另外，它还是对外展示的“标杆”，应用进程可调用 poll() 或 ioctl(DRM_IOCTL_WAIT_VBLANK) ，等待一帧的完成，进行同步操作。
还有，它也是检测显示性能的关键。

结合上图来理解，fb_helper 的主要作用就是充当 FrameBuffer 框架与 DRM KMS 框架之间的中间节点。
根据 FrameBuffer 框架的特性，又或者从驱动开发来说：因为我们最终要在显示屏中显示出图像，必然需要知道显示屏本身，即它的显示参数，最基本的有：显存地址、分辨率、消隐区、BPP 和像素时钟等，需要把这些参数写到 LCD Controller 寄存器，LCD Controller 才能根据这些参数发送正确像素数据，使显示屏正常显示图像。
当然，这些设置操作我们可以直接通过 DRM 框架去设置。如果使用 DRM 框架生成一个 FBDEV 来使用，则需要在 FrameBuffer 框架与 DRM 框架之间添加一个中间层，使得当我们通过 FBDEV 设置显示参数时，通过这个中间层传参。这个中间层的对象就是 drm_fb_helper ，内有 drm_client_dev ，对应 DRM KMS ；另有 drm_client_buffer ，对应 DRM GEM 。
在 DRM driver 初始化的过程中，比如 IMX8MP ，它调用了 drm_fbdev_generic_setup() 来模拟出一个 FBDEV 设备。通常来说，这个设置一般是在系统初始化使用（内核和文件系统服务的初始化）。在此函数调用期间，把 DRM 和 FrameBuffer 的设置参数和初始化流程过了一遍。这个 FBDEV 通常是给把 LOGO 显示在屏幕，或初始化信息输出到屏幕。DRM 更多的注重在启动后的使用操作。

fb_helper 其实是在 DRM 根据生产者和消费者机制，fb_helper 充当生产者，Framebuffer 充当消费者。

其实可以把 fb_helper 当作是在内核态使用 DRM 的程序。换句话说，就是在用户进程通过 ioctl 操作 DRM 的步骤和过程是和它类似的。为什么可以这样理解？当 DRM 驱动已初始化好它自己的 ‘possible_pipelines’ 后，就是已经把 plane 、crtc 、encoder 、connector 初始化完成后，就可以使用了。但在 atomic commit 前，需要调用 drm_helper_probe_single_connector_modes() 检测 connector 的连接状态和获取显示参数，后面就分配显存，就可以发送 atomic commit 。fb_helper 的操作步骤就是如此，在应用层中使用 ioctl 操作步骤也是类似的。
但这样说还是很笼统，又或者说 fb_helper 和应用层用 ioctl 操作的相同特征点是什么？
先说应用程序，需要先打开 /dev/dri/cardX ，再通过 ioctl 调用 drm_helper_probe_single_connector_modes() 检测连接状态和获取显示参数。
同理，fb_helper 也是需要先调用该函数去检测和获取。
下一步，应用程序通过 mode_set 确定 pipeline ，就是用哪个(些) crtc(s) 、encoder(s) 去显示。
fb_helper 也是类似。不同的是，如果硬件支持多屏显示，则会做一些兼容操作，比如说哪个屏幕的分辨率最大，就用该分辨率去获取显存；显示屏幕时为了确保最小的屏幕也能正常显示，会让所有屏幕都用最小屏幕支持的分辨率来显示。
然后到获取显存时，看 fb_helper 的代码、结构体 drm_client_dev 和获取显存的接口函数（drm_mode_create_dumb()）可知，获取显存是需要 drm_file 。应用程序同理，也是通过 ioctl 去获取显存，其 struct file *filp ，对应一个 drm_file ，这个是在 open() 期间创建的。使用 drm_file 去获取显存。

看 GEM 了解 drm_file 和 GEM 的关系。

从 GEM 获取到显存后，不管是 fb_helper 还是应用程序，都需要用 drm_framebuffer 去建立 plane 和 drm_gem_object 的关系，期间会调用 drm_mode_addfb() 或 drm_mode_addfb2() 。

综上所述，fb_helper 就是应用程序使用 ioctl 去操作 DRM 的步骤的一个“缩影”。初学者可以看 fb_helper 的代码去学习 DRM 的操作流程，了解一下大致，不推荐详细看，仅需要围绕上面的步骤去看就好。
